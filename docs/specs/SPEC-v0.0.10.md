**FR-25 (App updates)** — **new** (the reserved scope since DR-47 — the `FR-22`+ chain, re-seated by OQ-46 (closed A) and OQ-52 (answered A) to `FR-25`+ — joins this release at the user's decision of 2026-11-12, DR-321; the reservation ends at its own consumption).
*The app maintains itself up to date. On startup the app checks silently in the background whether a newer published version exists: the check never delays a window opening, never blocks any interaction, and asks nothing of the user when the app is current or the source is unreachable. The main window's Settings menu carries a **Check for updates** action that runs the same check on demand and always reports its result. When an update is found the app presents it — the new version and the release notes — and offers to install it: the app downloads the update with visible progress, verifies its signature, installs it through the platform installer, and the app exits for the installation. A manual check that finds the app current reports exactly that. A manual check whose update source is unreachable surfaces a typed error as a toast. The update source is the app's GitHub Releases update manifest (`dong-nz/pdf-keeper`, the signed `latest.json`); signing and publishing are the maintainer's release process (§3.11), not app features. No reader window carries update controls — the update is app-global, acted on from the main window.*

**UI-52 (Update surfacing and flow)** — **new**.
*Updates are surfaced only through released components: the Settings menu gains a **Check for updates** item (UI-15 menu rules); a found update opens the app's own update affordance — the new version, the release notes text, and an **Install** action; the download shows progress through the released job-progress affordance (UI-12), and its completion carries the install launch and the app's exit for the installer; "up to date" and unreachable-source results are toasts (UI-16 rules). No new visual language, no new dialog class: menu item, toast, progress bar — all released components. The startup check renders nothing on its own; it only arms the availability affordance (a quiet toast with the Install action), never a modal, never on reader windows.*

### 3.2 Store (`reader.svelte.ts`)

`ReaderViewMode` gains `"horizontal"`. The `currentPage` derivation gains the horizontal branch: the same page-geometry table the continuous mode already maintains, evaluated against the row's horizontal scroll position (the DR-155 single-source rule unchanged — one source, one derivation). `goToPage` in this mode sets the horizontal scroll target (its preview→full landing rule unchanged). `stepPage`, `scrollViewport`, `scrollNotch` need no logic change — they already delegate to `goToPage`/`onScrollBy`; the view supplies the axis.

### 3.3 View (`ReaderView.svelte`)

A horizontal layout branch: a flex row, pages at their current zoom size with the 12 px gap (`CONTENT_GUTTER`), the row vertically centered (the released centering pattern on the other axis). The view registers `onScrollBy` as `scrollBy(±delta, 0)` in this mode and the viewport-page count for `scrollViewport` is computed from the viewport width instead of height. The mount window windows pages on the x-axis with the same `OVERSCAN` bound (the released mount rule, UI-04/NFR-09 pattern); prefetch keeps the released request order with the row direction as movement direction. ### 3.8 ToC pin (UI-49)

- **State**: two booleans on the **host window's store** — `tocPinned` (the layout mode) and `tocDockedOpen` (the docked panel's visibility, DR-337; the name avoids the existing `tocVisible()` entries-list method) — the reader store for the PDF reader, the `epubReader` store for the EPUB reader (each store is the single source of its window's view state — DR-155; the docked layout must be known to the view to re-lay out the content column, so component-local state is the wrong home). Both default `false`; the released overlay open/close state stays where it is today. **OQ-60 closed → A (DR-327): the pin is session-scoped per window** — every new reader window starts unpinned (the OQ-44/DR-181 session-scoping pattern); no settings field. `setTocPinned` is the single pin path and writes visibility with it (pin → visible, un-pin → closed); `setTocDockedOpen` is the visibility path the strip control and the docked panel's `Esc` use. The panel is rendered when `tocPinned && tocDockedOpen`.
- **Layout**: the reader window's page area becomes a two-column region when pinned — the panel column (fixed width, a design token set at build and recorded per R9.1) at the left edge from below the chrome strip to the control strip, and the content column beside it. Chrome and control strips span the whole window unchanged. - **Panel**: same component, same tree, same toolbar row; the pin control is a right-end toggle in that row (`aria-pressed` like the mode buttons, static accessible name), its glyph following the state — `pin` when pinned, `unpin` when not (DR-336). The docked presentation renders flush: the toolbar row carries no corner rounding (the rounded top corners belong to the floating overlay recipe, DR-226) and its vertical padding is 4 px, not 8 (DR-335). Entry selection in the pinned state navigates and keeps the panel open; the overlay's close-on-select applies only in the unpinned state. The strip control in the pinned state reflects the visibility (`aria-pressed` = visible) and toggles it **keeping the pin**; the panel's pin control is the only un-pin path (DR-337).

# SPEC-v0.0.10 — Continuous-horizontal reading mode (PDF reader)

**Status: ON-GOING** (approved + build opened by the user's "implement" 2026-11-16, DR-328; drafted 2026-11-11 in advance at the user's request; the registry row in `docs/specs/INDEX.md` is the authority; scope extended 2026-11-12 by the user's decisions recorded at `SPEC-v0.0.9.md` DR-314 and in this spec's DR-320/DR-321, and 2026-11-16 by DR-327; the baseline reconciliation ran 2026-11-16, DR-326; no open questions remain). ## 2. Requirements

**FR-17 (Built-in PDF reader)** — **MODIFIED** (the mode enumeration only).
Old text (RELEASED, `SPEC-v0.0.9.md` §2 new text — re-quoted verbatim from the frozen spec at the 2026-11-16 reconciliation pass, DR-326; OQ-54 closed → A left the text as quoted at drafting): *"The app displays and reads PDF documents inside itself: opening a document shows its pages in a dedicated reader window (one window per document — OQ-37 closed, DR-139), navigable to every page and zoomable (fit-width and fixed zoom steps), and viewable in the mode the user selects: single page, continuous, or facing (UI-34). Reading does not require an external application. Opening a document with the OS default application remains available as an explicit action. For EPUB documents, activation opens the app's own EPUB reader (FR-23). A document whose file is missing, or a file that cannot be rendered, never opens silently: the typed error paths of FR-08 apply, and an unrenderable file additionally offers the external-open action."*
New text: identical except: *"…and viewable in the mode the user selects: single page, continuous, facing, **or continuous horizontal** (UI-34)."*

**UI-34 (View modes)** — **MODIFIED**.
Old text (RELEASED, `SPEC-v0.0.7.md` §2, as amended at build by DR-204/DR-205/DR-219/DR-224/DR-227): *"The reader control strip carries a view-mode control after the zoom group: three icon-only buttons with tooltips — single page, continuous, facing — with the active mode rendered active. Continuous is the default and is the released behavior: pages form a continuous vertical scrollable stack, horizontally centered in the viewport area (clause added at build by DR-205). Single page shows exactly one page at a time: the page is centered horizontally, and centered vertically when it fits the viewport area — a page taller than the viewport is top-aligned and the container scrolls, vertically always and horizontally when zoomed beyond the width (amended at build by DR-204…); continued scrolling at a content edge navigates (clause amended at build by DR-227…): the first wheel event whose direction points past the reached edge advances exactly one page in that direction, through the same navigation path as the controls — no distance accumulation is required, and one wheel event never advances more than one page; scrolling within a page taller than the viewport is unchanged, and a backward step lands at the previous page's bottom edge as before. Navigation controls remain: prev/next, the page field, PgUp/PgDn (previous/next page) and Home/End (first/last page). The pages around the current one are served ahead of the navigation (clause added at build by DR-219, its window extended by DR-224…): once the current page is served, the current page ± 6 window (clamped to the document bounds) is requested at the current display width in the released request order (NFR-08/DR-150 — the current page leads its queue; the window is queued movement-direction-first)… The mount stays exactly one page… Facing lays pages out side by side in consecutive pairs in reading order (1|2, 3|4, … — OQ-43 closed → DR-180), each row centered horizontally (DR-205); pairs stack vertically with the same 12 px gap and scroll like the continuous stack; prev/next and PgUp/PgDn move one pair at a time; the page field shows the first page of the pair containing the viewport center, and entering a number opens the pair containing that page; a last page with no partner renders alone. Fit-width fits the visible unit to the viewport (in facing, each page at most half the viewport width minus the gap); zoom steps apply to each page. Changing mode keeps the current page visible and re-lays out around it. View modes are session-scoped (OQ-44 closed → DR-181): a mode choice applies to the open reader window; every new reader window opens in continuous. Page serving, the mount rule (UI-04), the page cache and the measured budgets are mode-independent: every visible page is served through the released pipeline."*
New text: the released text with these changes:
- *"…carries a view-mode control after the zoom group: **four** icon-only buttons with tooltips — single page, continuous, facing, **continuous horizontal** — with the active mode rendered active."*
- After the facing clause, a new mode clause: **"Continuous horizontal** lays pages out side by side **in a single horizontal row in reading order, left to right**, at the current zoom, with the same 12 px gap between pages as the vertical stacks; **the row is vertically centered in the viewport area (the horizontal counterpart of the DR-205 centering)** and **scrolls freely horizontally — the continuous model on the horizontal axis. This mode is never the default.** **In continuous horizontal: the page field shows the page containing the viewport's horizontal center, and entering a number opens that page; prev/next step one page along the row; `PgUp`/`PgDn` advance the view one viewport along the row direction (the released viewport-step rule, horizontal axis); fit-width fits the current page — the one the horizontal position names — to the viewport width; zoom steps apply to each page.**"
- The serving clause (DR-219/DR-224) applies **on the horizontal axis in this mode, the row direction being the movement direction**; the mount-window bound is the released bound on the other axis.
- **Edge navigation (DR-204/DR-227) is single-page-mode behavior; it does not apply to continuous horizontal** (it has no single-page edges).
- Unchanged: the default (continuous), the mode-switch handoff ("Changing mode keeps the current page visible and re-lays out around it" — in this mode that means the current page is scrolled into the row's viewport), session scoping (OQ-44/DR-181: a new reader window still opens in continuous), the mode-independent serving/cache/budgets closing clause.

**UI-39 (Reader keyboard navigation)** — **MODIFIED**.
Old text (RELEASED, `SPEC-v0.0.7.md` §2): *"In any reader window the arrow keys navigate: ArrowLeft/ArrowRight act exactly as the strip's previous/next controls — one page, one pair in facing mode — through the same navigation path the controls use; ArrowUp/ArrowDown are the wheel's keyboard counterpart, one notch (100 CSS px) per key press: in continuous and facing modes they scroll the stack by that notch; in single-page mode they follow the edge rule of UI-34 as amended by DR-227 — within a page taller than the viewport they scroll the container by the notch, and at a reached content edge the first such press advances exactly one page in that direction, landing as the wheel does (a backward step lands at the previous page's bottom edge). **FR-24 (Reader surface conveniences)** — **new** (consumes the reserved ID at `FR-24`+; the user's enhancement requests of 2026-11-12, folded in by the user's decision DR-314; design §3.8/§3.9).
*The reader windows offer two surface conveniences: the table-of-contents panel — in the PDF reader and, per the user's decision of 2026-11-16 (DR-327), in the EPUB reader too (UI-48 as modified) — can be pinned as a persistent panel docked at the left edge of the reader window (UI-49), and the PDF reader's control strip carries a settings control whose menu exposes the reader surface's settings — at this release the theme switch, the same control the main window's settings menu carries (UI-50). **UI-49 (ToC panel pin)** — **new**.
*The ToC panel's toolbar row carries a pin control at its right end — icon-only with a tooltip (UI-13), rendered with the released toggle affordance, its pressed state reflecting the pin. The panel is the shared `TocPanel` component (M9): the pin lands in **both** hosts — the PDF reader's panel and, per the user's decision DR-327, the EPUB reader's (UI-48 as modified). Unpinned is the released behavior: the panel is a transient overlay anchored to the ToC control, closed by an entry selection, by `Esc` (the released overlay-priority guard) or by the control toggle. **Pinning** re-lays the panel out as a persistent panel docked at the reader window's left edge, spanning from below the chrome strip to the control strip at a fixed width (the value is a build-time design decision recorded per R9.1); the page area re-lays out beside it — the content box shrinks, and every mode's layout, fit-width derivation, mount window and serving follow the shrunken content box under the released content-box rules (unchanged in kind); in the EPUB host the reading column narrows and the reflowable text re-wraps — no other surface change. While pinned the panel stays open across entry selections (the overlay's close-on-select does not apply) and across mode changes. The pin control stays at the toolbar row's right end in both states; activating it again returns to the released overlay behavior (the panel closes; reopening uses the released anchor). Closing a pinned panel by `Esc` or the ToC control resets it to the unpinned state; the pin is per window and not inherited by new windows (OQ-60 closed → A, DR-327). The pin is orthogonal to the view mode and works in all four modes, including continuous horizontal.*

**UI-50 (Reader settings menu)** — **new**.
*The **PDF reader's** control strip carries a settings control at its right end (after the view-mode group) — icon-only with a tooltip (UI-13), opening a menu built with the released menu kit (UI-15 rules). The EPUB reader's strip stays the released three controls (the UI-48 MODIFIED row changes its panel clause only). The menu's items are the reader surface's settings; at this release it carries exactly one item — the theme switch, the released control (UI-17 as modified by SPEC-v0.0.7 §3.13, DR-209): the item displays the theme currently in effect and advances one step of the fixed cycle Light → Dark → Auto, the menu staying open across the activation. Every write goes through the settings store (R1.6): the change applies live in every open window through the released re-apply mechanism and persists exactly as the main window's switch. The menu is the extension point for later reader-surface settings; it carries no reader-unrelated items — no Settings… dialog, no About…*

**UI-51 (List-view cover, second enlargement)** — **new** (the user's request of 2026-11-12, recorded as DR-320; the same kind of change as UI-45/DR-278 — a Phase-B cover enlargement folded into a later release at the user's placement decision).
*The list row's cover is **100 px wide**; its height is computed from the A4 ratio (100 × 297/210 = **141 px**), and the row base is the cover plus the existing 8 px insets: **157 px**. This supersedes the values of UI-45 (v0.0.8 §2, DR-278: "the list row's cover is 75 px wide; its height … 106 px … the row base … 122 px") and re-derives the released row geometry the same way UI-45 did — the width is the design constant, the height follows the ratio, the row follows the cover. Everything else in the row is unchanged: the 18 px metadata-line step, the 8 px cover inset against the separator lines (AC-88), the 96 px meta column, the skeleton identity rule (AC-50), grid geometry, and the cover pipeline — no Rust change: the cached covers render at ≥ 560 px and scale down to 100 px without quality loss. The windowing math is untouched machinery; its test anchors re-pin at the new row (AC-150).*

**FR-25 (App updates)** — **new** (the reserved scope since DR-47 — the `FR-22`+ chain, re-seated by OQ-46 (closed A) and OQ-52 (answered A) to `FR-25`+ — joins this release at the user's decision of 2026-11-12, DR-321; the reservation ends at its own consumption).
*The app maintains itself up to date. On startup the app checks silently in the background whether a newer published version exists: the check never delays a window opening, never blocks any interaction, and asks nothing of the user when the app is current or the source is unreachable. The main window's Settings menu carries a **Check for updates** action that runs the same check on demand and always reports its result. When an update is found the app presents it — the new version and the release notes — and offers to install it: the app downloads the update with visible progress, verifies its signature, installs it through the platform installer, and the app exits for the installation. A manual check that finds the app current reports exactly that. A manual check whose update source is unreachable surfaces a typed error as a toast. The update source is the app's GitHub Releases update manifest (`dong-nz/pdf-keeper`, the signed `latest.json`); signing and publishing are the maintainer's release process (§3.11), not app features. No reader window carries update controls — the update is app-global, acted on from the main window.*

**UI-52 (Update surfacing and flow)** — **new**.
*Updates are surfaced only through released components: the Settings menu gains a **Check for updates** item (UI-15 menu rules); a found update opens the app's own update affordance — the new version, the release notes text, and an **Install** action; the download shows progress through the released job-progress affordance (UI-12), and its completion carries the install launch and the app's exit for the installer; "up to date" and unreachable-source results are toasts (UI-16 rules). No new visual language, no new dialog class: menu item, toast, progress bar — all released components. The startup check renders nothing on its own; it only arms the availability affordance (a quiet toast with the Install action), never a modal, never on reader windows.*

### 3.2 Store (`reader.svelte.ts`)

`ReaderViewMode` gains `"horizontal"`. The `currentPage` derivation gains the horizontal branch: the same page-geometry table the continuous mode already maintains, evaluated against the row's horizontal scroll position (the DR-155 single-source rule unchanged — one source, one derivation). `goToPage` in this mode sets the horizontal scroll target (its preview→full landing rule unchanged). `stepPage`, `scrollViewport`, `scrollNotch` need no logic change — they already delegate to `goToPage`/`onScrollBy`; the view supplies the axis.

### 3.3 View (`ReaderView.svelte`)

A horizontal layout branch: a flex row, pages at their current zoom size with the 12 px gap (`CONTENT_GUTTER`), the row vertically centered (the released centering pattern on the other axis). The view registers `onScrollBy` as `scrollBy(±delta, 0)` in this mode and the viewport-page count for `scrollViewport` is computed from the viewport width instead of height. The mount window windows pages on the x-axis with the same `OVERSCAN` bound (the released mount rule, UI-04/NFR-09 pattern); prefetch keeps the released request order with the row direction as movement direction. Scroll anchoring follows the released mechanism on the horizontal axis (DR-152, as extended by DR-282's pre-change-geometry re-anchor). **The two-stage serving pipeline this mode inherits is the shipped one** (the reconciliation pass, DR-326): the preview stage at the page's CSS display width (`min(…, PREVIEW_WIDTH_MAX)`, DR-151/DR-153 — the rule reads the page's display width at the current zoom, identical in the row), the full stage arriving as the cross-fade overlay (DR-316/DR-318/DR-319) and promoted to the base `src` with the preview released 600 ms after the fade begins (DR-323) — this machinery is per-page and layout-agnostic, unchanged by this mode; the AC-147 lane measures against the post-promotion single-raster steady state (the DR-323 profile the AC-73/AC-75 budgets were re-calibrated against).

### 3.4 Controls (`ReaderControls.svelte`)

`MODE_BUTTONS` gains the fourth entry after facing. The icon glyph and the i18n key are defined at build and recorded per R9.1 (the D27 pattern — a small design decision, not an OQ). Everything else on the strip is untouched — page field (its derivation now comes from the horizontal position), prev/next, zoom group, ToC control — except the settings control **UI-50** adds at the strip's right end (§3.9).

### 3.5 What does not change

Default mode; session scoping; the serving pipeline, page cache and measured budgets; the ToC panel's tree content and selection behavior (its presentation gains the docked state — UI-49, §3.8); error paths; single-page edge navigation; the keyboard map's structure (same methods, per-mode meaning); the EPUB reader's flow (UI-48 stays vertical — horizontal flow is a PDF concept; reflowable text has no page row) and the EPUB reader's strip (the settings menu lands on the PDF reader's strip only — the EPUB strip stays the released three controls). The ToC pin lands on **both** readers: `TocPanel` is one shared component (M9) and the EPUB side enters as the UI-48 MODIFIED row per the user's decision DR-327 (§2) — the deferral this draft carried at §3.5's earlier text is closed by that decision.

### 3.8 ToC pin (UI-49)

- **State**: a `tocPinned` boolean on the **host window's store** — the reader store for the PDF reader, the `epubReader` store for the EPUB reader (each store is the single source of its window's view state — DR-155; the docked layout must be known to the view to re-lay out the content column, so component-local state is the wrong home). Default `false`; the released overlay open/close state stays where it is today. **OQ-60 closed → A (DR-327): the pin is session-scoped per window** — every new reader window starts unpinned (the OQ-44/DR-181 session-scoping pattern); no settings field.
- **Layout**: the reader window's page area becomes a two-column region when pinned — the panel column (fixed width, a design token set at build and recorded per R9.1) at the left edge from below the chrome strip to the control strip, and the content column beside it. Chrome and control strips span the whole window unchanged. The content box shrinks in the DOM; the released fit-width and mount-window machinery measure the content box (M3), so zoom fitting and serving follow the shrunken box with **no pipeline change** — this is the same mechanism the sidebar-less reader already uses, just with a docked sibling.
- **Panel**: same component, same tree, same toolbar row; the pin control is a new right-end toggle in that row (`aria-pressed` like the mode buttons). In the docked state the panel is not an `OverlayAnchor` popup — it is layout; it still registers with the window's `Esc` guard so `Esc` closes it first (M7's priority rule extended to the docked state). Entry selection in the pinned state navigates and keeps the panel open; the overlay's close-on-select applies only in the unpinned state.
- **Modes**: the pin is orthogonal to `viewMode`; in continuous horizontal the row centers vertically in the shrunken content box (§3.3 unchanged, measured against the smaller box).
- **EPUB host (UI-48 MODIFIED, DR-327)**: the same `TocPanel` component carries the pin in both hosts (M9); no per-host branch in the panel itself. The docked state narrows the reading column — the reflowable flow re-wraps; the mount-window chapter sizing and the position model (v0.0.9 §3.13) measure the narrower column, no other change. The strip's three controls, the keyboard map, the typography tokens and the named exclusions are untouched.

### 3.11 App updates (FR-25, UI-52)

- **Dependency (approved by the user's option-A answer, DR-321 — the AGENTS §2 approval):** `tauri-plugin-updater` — the official Tauri plugin, Rust crate registered in `src-tauri/Cargo.toml` + `@tauri-apps/plugin-updater` in `ui/package.json`, pinned to the same version line as the pinned Tauri 2.12.5. Its own transitive tree (HTTP client, `minisign-verify`) belongs to the plugin, not to our manifest.
- **Config:** `plugins.updater` in `tauri.conf.json` — `endpoints: ["https://github.com/dong-nz/pdf-keeper/releases/latest/download/latest.json"]`, `pubkey`: the base64 minisign public key generated at the build's start; the private signing key stays outside the repository with the maintainer (its handling recorded in the release-process notes at Ship). The plugin verifies the manifest signature before anything is shown.
- **Flow (R1.2/R1.3 shape):** the plugin's own commands are the command surface — whitelisted through the pattern the opener plugin already established (UI-40): the frontend calls `check()` and `downloadAndInstall()` through the plugin's typed JS client; the network fetch, version comparison, signature verification, download and installer launch all run in the plugin's Rust side. No hand-written `app_*` commands, no business logic in the frontend beyond surfacing. Startup: the main window's post-first-paint effect calls `check()` async — off the UI thread by construction, nothing awaits it; a found update arms the availability toast with the Install action. Settings menu: the *Check for updates* item runs the same call path and reports every result (update found / up to date / typed error toast).
- **Install (Windows):** `downloadAndInstall` streams progress events → the released job-progress affordance (UI-12); completion runs the platform installer (MSI/NSIS silent flags) and the app exits — the plugin handles the launch; the app adds no restart machinery.
- **Release process (operational, not app code):** `tauri build` with `TAURI_SIGNING_PRIVATE_KEY` set produces the signed artifacts; `latest.json` (version, platform artifact URLs + signatures, release notes body) is published with each GitHub Release — by hand for this release, automatable when the roadmap's CI line lands. The maintainer-side steps are recorded in the technical reference at Ship.
- **Tests (R6):** a new `flowAppUpdate` lane points the updater at a **harness-served fixture endpoint** (a local HTTP server serving a fixture `latest.json` + a small signed fixture artifact, built by `scripts/` per D15): newer-version manifest → the availability affordance with version + notes + Install; current-version manifest → the "up to date" toast; unreachable endpoint → the typed error toast; download + install invoked on the fixture artifact → progress rendered, app exits for the install (AC-151/152). Startup non-blocking: the main window's activation timing measured with the startup check in flight against a reachable and an unreachable fixture endpoint (AC-153). The real GitHub endpoint is exercised in Phase B by the user, not in the lane.

## 5. Open questions

**OQ-60 (persistence of the pinned ToC state) — CLOSED → A** (opened 2026-11-12 with DR-317; **closed by the user 2026-11-16, answer A — DR-327**). Does a reader window that opens a pinned ToC panel make the next reader window start pinned? **Answer: no — option A, session-scoped per window.**
- **Option A (chosen): session-scoped, per window** — every new reader window starts unpinned; the pin lasts for the window's lifetime. Consistent with the released reader-state model (OQ-44/DR-181: view modes are session-scoped; OQ-45: no per-document persistence) — the pin is a view-layout state like the mode, not a setting. No settings-store change.
- **Option B (declined): app-wide persisted setting** — the pinned state is stored with the settings and every new reader window opens with the panel docked. Treats the dock as a user preference; it adds a settings field and a layout that changes by default, surprising users who pinned once incidentally.

The three mode-design forks were decided by the user on 2026-11-11 (ask-form answers, recorded as DR-290): (1) placement — a dedicated v0.0.10, shipped after v0.0.9; (2) semantics — continuous horizontal (the film-strip variant rejected); (3) RTL — deferred to the roadmap.

## 2. Requirements

**FR-28 (Reader position memory)** — **new** (the gap named in every release-notes page since v0.0.6: "the reader remembers nothing between sessions"; ROADMAP §3 line 6's named scope).
*The app remembers where the user stopped reading, per document, and returns the reader window to that point when the document is opened again. It applies to both reader kinds (PDF and EPUB). The memory lives in the app's settings store as a per-document key — it is app state, not library data: deleting a document removes its memory; relinking or renaming keeps it (the id is unchanged). The memory updates while reading (debounced, last value wins) and is flushed when a reader window closes. On re-open the remembered position is applied before the first page paints — no visible stop at page 1. A remembered position outside the document's current extent (a relink to a shorter file) clamps to the nearest valid position. No position UI is added: no prompt, no recently-read list, no library-side affordance — opening the document simply resumes it.*

**FR-29 (Reader view-mode memory)** — **new**. *(OQ-68 closed as A — DR-399: the user-level-preference shape below is confirmed.)*
*The reader's view mode becomes a remembered preference: the mode the user last chose is the mode new reader windows open in, across documents and restarts, for both reader kinds. Until the user first chooses a mode, the released default (continuous, M2) is unchanged. Choosing a mode remains a per-window action exactly as today (UI-34 controls unchanged); the memory changes only what a new window starts with.*

**FR-30 (Text selection and copy in the reader)** — **new** (the ROADMAP §3 line 6 item "text selection and copy in the reader").
*The reader gains text selection. In a PDF that carries text, the user can select words and lines over the rendered page and copy the selection to the system clipboard (`Ctrl+C`). In the EPUB reader, the reading column's text is selectable and copyable. The selection is the document's own text: for PDFs it is the embedded text layer extracted by the app's bundled PDF engine — a page without embedded text (a scan) gets no selectable layer, and this release adds no OCR. Selection works in all four PDF view modes and follows zoom changes. Selection must not change any released reader behavior: scrolling, page navigation, zoom, keyboard navigation, ToC jumps and window plumbing behave exactly as today. The visual language is unchanged: the page stays the rendered image; selected text paints in the theme's selection color.*

**UI-54 (Reader text-selection surface)** — **new**.
*The text layer is invisible until used: pages render exactly as today, and transparent selectable text sits over them at the text's real coordinates (derived from the document's own geometry — no measurement). Dragging selects; the selection paints with the theme's selection token; `Ctrl+C` (or `Ctrl+Insert`) copies. The EPUB reading column becomes selectable as a scoped exception to the app's global no-selection rule (the released scoped-override pattern, M5); its existing interactions (scroll, navigation, links) are unchanged. No "select all on page" control, no selection persistence, no in-document search.*

**FR-31 (Manual cover selection)** — **new** (the user's request of 2026-11-19: "some epub or pdf cannot render cover or the cover not what expected. can introduce a feature to update cover by selecting a page in the document?"; recorded as a candidate in ROADMAP §6; the user's scope decision the same day — depth PDF page selection + EPUB embedded-image selection, folded into this release, DR-402).
*The app lets the user choose what represents a document in the library. For a PDF: any page shown in the reader can be set as the document's cover. For an EPUB: the cover can be picked from the raster images embedded in the book (the formats the cover pipeline can already decode — PNG and JPEG); a book with no such images keeps the released behavior (declared cover, or the generic glyph). The choice is stored with the document and survives restarts; an **Automatic cover** action reverts to the released behavior (first page / declared cover). The chosen cover renders through the existing background cover pipeline — setting a cover never blocks the app; a failed render leaves the generic glyph (the designed recovery, R5.3). The staleness model stands (DR-113): a changed file re-renders the chosen cover with the choice kept; a chosen page outside the document's current extent falls back to the automatic cover at render time, the choice kept (a later file change can make it valid again); a choice made for a document whose file is missing is kept and renders on relink. The document's file is never modified. Automatic covers — for every document the user did not touch — behave exactly as released, cache keys byte-identical (no re-render after this change).*

**UI-55 (The cover-selection surfaces)** — **new**. *(OQ-73 closed with the user's own shape — DR-403: neither drafted option; the user named a dedicated cover menu in the reader's top strip plus a context-menu picker in the main window.)*
*Two surfaces, one mechanism. **Reader**: the chrome strip gains a dedicated cover menu — a new control joining the right-end control cluster on every platform (the same edge the app menu and the reader settings control keep; on macOS the whole chrome moves per UI-07 MODIFIED §3.7 and the cover menu moves with its cluster). In the PDF reader its items are "Set this page as cover" (the page currently shown) and "Automatic cover"; in the EPUB reader, "Choose cover…" (opens the image grid) and "Automatic cover". **Library**: the document context menu (row, card) gains "Update cover…", which opens the cover picker: for a PDF, a lazily filled strip of page thumbnails (small renders streamed in as the strip scrolls — the existing page-render path at picker size, background, nothing blocks); for an EPUB, a grid of the book's embedded images (served through the existing book-image path); both carry "Automatic cover". A pick sets the choice; the card updates through the existing cover-appearance mechanism (the glyph until the render lands, then the chosen cover). No cover-management screen; the commands validate and return — the rendering is pipeline work.*

**NFR-12 (CI/release pipeline run-time and cache reuse)** — **new**. *(OQ-71 closed as A — DR-399: a new line, as drafted; NFR-10/NFR-11 stay frozen.)*
*The repository's CI and release pipelines reuse warm caches across runs and across the two workflows: the Linux dependency step is cached against the dependency list so a cold runner pays it once; the Rust build cache is shared between `ci.yml` and `release.yml` so a recent `master` push warms what a tag build consumes; the pnpm store cache keyed by the lockfile stays as verified already in place (M8). The run-time contract is measured, not asserted — the AC-158 wall-clock reporting is the instrument: the release run's Linux job at or below **≈ 400 s** against the 1 380 s measured 2026-11-18 (same machine class; §3.1 M9's warm-build floor is the floor). The hosted macOS runner queue is out of scope (operational, ROADMAP §4).*

### 3.2 Position and view-mode memory (FR-28, FR-29)

- **Storage — settings keys, as the ROADMAP line names.** Keys `reader.pos.<id>` with a compact JSON value: PDF `{"p":<1-based page>,"o":<0–1 offset fraction within the page>}`; EPUB `{"c":<1-based spine index>,"o":<0–1 fraction within the chapter>}` (OQ-72 closed as A, OQ-69 closed as A — DR-399: the value shapes below are confirmed). One key per read document, values are numbers only. `delete_documents` (M10) deletes the keys of the deleted ids **in the same transaction** (R2). Relink/rename keep the id, so the memory survives them; a shorter relinked file clamps on open.
- **Access — two new thin commands (R1.2):** `reader_position_get(id)` (returns the stored value or null; the id must exist) and `reader_position_set(id, value)` (validates the JSON grammar and bounds before writing). They deliberately do **not** emit `settings_changed`: a position is per-document state, not a window setting, and one reader window per document (M1) means no cross-window sync is needed. `app_get_settings` is untouched — it is typed (M3), so the new rows never reach it and its payload cannot bloat.
- **Write path (reader store):** on page change and on scroll settle, write through the released debounce utility (1 s); flush on `pagehide` (window close/exit). Last value wins; no history. The last ≤ 1 s of reading may be lost on an abrupt app exit — accepted and stated.
- **Restore path:** the reader bootstrap already fetches the document's page count / spine manifest before the first page request (released flow). The store reads `reader_position_get` and sets the current page + offset **before the first paint** — clamped to `[1, pageCount]` / `[1, spine count]`. Per mode: single/continuous/horizontal anchor the page top plus `o ×` the page's computed display height (exact geometry, M4); facing anchors the pair containing the page; EPUB scrolls to the chapter host then `o ×` its measured height once mounted (M6). No visible stop at page 1 (AC-167's check).
- **View mode (FR-29, option A shape):** a settings key `reader.view_mode` validated against the four mode names with the released default (`continuous`, M2) when absent — the exact typed-filter pattern `get_settings` already uses for `view`/`sort`/`dir` (M3): add `view_mode` to `SettingsDto`; every window already reads settings at startup, so a new reader window constructs its store from the remembered mode; `setViewMode` writes through the existing settings store path (debounced batch, as `view`/`sort` writes today). The rejected option B would have swapped `reader.view_mode` for `reader.mode.<id>` with the same cleanup as positions; OQ-68 closed as A (DR-399).
- **Size:** bounded by the library (one small row per read document); no cap, no privacy line (numbers only).

### 3.3 Text layer and selection (FR-30, UI-54)

- **Rust (`pdf` module extension):** `page_text(...)` → `Vec<TextRun { text, x, y, w, h }>` from the pdfium segment API (M7): iterate `page.text()` segments, take `text()` + `bounds()`, convert PDF bottom-origin rects to **top-origin page-point coordinates** (flip with the page height — the same coordinate space the frontend's geometry math already uses, M4). Caps: at most 4 000 runs per page (a `truncated` flag beyond), a per-window-session LRU mirroring the page-image cache. New **async** command `app_pdf_text(id, page)` (off the UI thread like `app_pdf_page`), DTO `{ runs, truncated, page_width_pt, page_height_pt }`; added to the R1.3 whitelist and the typed client. Password-protected PDFs: the released FR-20 password store feeds the same unlock path page rendering uses — text extraction reuses it, no new prompt.
- **Frontend — `TextLayer.svelte` per rendered page:** absolutely positioned spans, transparent color, `user-select: text`, `::selection` painted with the theme's selection token; positions derived arithmetically from the store's exact geometry (scale = display width ÷ page width pt; top-origin coordinates) — re-derived on zoom and mode change, never measured. Requested lazily for pages entering the render window, same request discipline as page images; cached per window session. Pages with no embedded text get no layer and no message (a scan simply stays as today).
- **Copy:** native selection + `Ctrl+C` / `Ctrl+Insert` — the webview's own clipboard path. No clipboard dependency, no Tauri clipboard code. ### 3.6 Pdfium bind path (D34)

- **Verified facts (2026-11-19, against the published v0.0.11 artifacts).** The macOS `.app` carries the library at `Contents/Resources/binaries/libpdfium.dylib` while the binary is `Contents/MacOS/bookkeeper`; the `.deb` installs `/usr/bin/bookkeeper` with the library at `/usr/lib/Book Keeper/binaries/libpdfium.so`. `pdf::bind_candidates` (`src-tauri/src/pdf/mod.rs`) searches `<exe_dir>`, `<exe_dir>/binaries`, `<cwd>/binaries`, then `Pdfium::bind_to_system_library` — both packaged layouts miss every candidate; the single owner stays `None`, every PDF read answers `PdfUnopenable` and every cover job fails. Windows (NSIS copies resources next to the exe) and AppImage (resources mount at the binary's root) hit today's search path; their behavior must not change. The bundle config (`tauri.conf.json` `"resources": ["binaries/*pdfium*"]`) is correct and stays — only the search path is wrong.
- **The change (Rust core only).** Make the candidate list a pure, injectable function: `bind_candidates(exe_path, cwd, extra_dirs) -> Vec<PathBuf>`; the no-argument call sites today become thin wrappers supplying the real process values, so the source-tree and next-to-binary behavior is untouched. `pdf::start_service` gains one parameter — the extra search directories. In `lib.rs` setup, where the service starts (the single-owner design §3.1 unchanged), resolve the managed resource directory (`app.path().resource_dir()`) and pass `vec![resource_dir.join("binaries")]`: `Contents/Resources/binaries` in the `.app`, `/usr/lib/Book Keeper/binaries` in the deb. The `pdf` module imports no Tauri type (R1.1) — the directory is plain data. `pdfium_binary_present()` (the test guard) keeps its current source-tree behavior through the same wrapper.
- **Rejected alternative:** deriving `exe_dir.parent()/Resources/binaries` from the executable path — macOS-only, leaves the `.deb` broken.
- **The class this defect exposes:** no test layer has ever run a packaged-app layout (CI runs the source tree, DR-390). The synthetic-layout units (AC-175) close the class mechanically; the real packaged-app run stays the user's hardware check, named honestly (the AC-174 pattern).

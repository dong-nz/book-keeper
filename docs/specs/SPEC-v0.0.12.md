## 2. Requirements

**FR-28 (Reader position memory)** — **new** (the gap named in every release-notes page since v0.0.6: "the reader remembers nothing between sessions"; ROADMAP §3 line 6's named scope).
*The app remembers where the user stopped reading, per document, and returns the reader window to that point when the document is opened again. It applies to both reader kinds (PDF and EPUB). The memory lives in the app's settings store as a per-document key — it is app state, not library data: deleting a document removes its memory; relinking or renaming keeps it (the id is unchanged). The memory updates while reading (debounced, last value wins) and is flushed when a reader window closes. On re-open the remembered position is applied before the first page paints — no visible stop at page 1. A remembered position outside the document's current extent (a relink to a shorter file) clamps to the nearest valid position. No position UI is added: no prompt, no recently-read list, no library-side affordance — opening the document simply resumes it.*

**FR-29 (Reader view-mode memory)** — **new**. *(OQ-68 closed as A — DR-399: the user-level-preference shape below is confirmed.)*
*The reader's view mode becomes a remembered preference: the mode the user last chose is the mode new reader windows open in, across documents and restarts, for both reader kinds. Until the user first chooses a mode, the released default (continuous, M2) is unchanged. Choosing a mode remains a per-window action exactly as today (UI-34 controls unchanged); the memory changes only what a new window starts with.*

**FR-30 (Text selection and copy in the reader)** — **new** (the ROADMAP §3 line 6 item "text selection and copy in the reader").
*The reader gains text selection. In a PDF that carries text, the user can select words and lines over the rendered page and copy the selection to the system clipboard (`Ctrl+C`). In the EPUB reader, the reading column's text is selectable and copyable. The selection is the document's own text: for PDFs it is the embedded text layer extracted by the app's bundled PDF engine — a page without embedded text (a scan) gets no selectable layer, and this release adds no OCR. Selection works in all four PDF view modes and follows zoom changes. Selection must not change any released reader behavior: scrolling, page navigation, zoom, keyboard navigation, ToC jumps and window plumbing behave exactly as today. The visual language is unchanged: the page stays the rendered image; selected text paints in the theme's selection color.*

**UI-54 (Reader text-selection surface)** — **new**.
*The text layer is invisible until used: pages render exactly as today, and transparent selectable text sits over them at the text's real coordinates (derived from the document's own geometry — no measurement). Dragging selects; the selection paints with the theme's selection token; `Ctrl+C` (or `Ctrl+Insert`) copies. The EPUB reading column becomes selectable as a scoped exception to the app's global no-selection rule (the released scoped-override pattern, M5); its existing interactions (scroll, navigation, links) are unchanged. No "select all on page" control, no selection persistence, no in-document search.*

**FR-31 (Manual cover selection)** — **new** (the user's request of 2026-11-19: "some epub or pdf cannot render cover or the cover not what expected. can introduce a feature to update cover by selecting a page in the document?"; recorded as a candidate in ROADMAP §6; the user's scope decision the same day — depth PDF page selection + EPUB embedded-image selection, folded into this release, DR-402).
*The app lets the user choose what represents a document in the library. For a PDF: any page shown in the reader can be set as the document's cover. For an EPUB: the cover can be picked from the raster images embedded in the book (the formats the cover pipeline can already decode — PNG and JPEG); a book with no such images keeps the released behavior (declared cover, or the generic glyph). The choice is stored with the document and survives restarts; an **Automatic cover** action reverts to the released behavior (first page / declared cover). The chosen cover renders through the existing background cover pipeline — setting a cover never blocks the app; a failed render leaves the generic glyph (the designed recovery, R5.3). The staleness model stands (DR-113): a changed file re-renders the chosen cover with the choice kept; a chosen page outside the document's current extent falls back to the automatic cover at render time, the choice kept (a later file change can make it valid again); a choice made for a document whose file is missing is kept and renders on relink. The document's file is never modified. Automatic covers — for every document the user did not touch — behave exactly as released, cache keys byte-identical (no re-render after this change).*

**UI-55 (The cover-selection surfaces)** — **new**. *(OQ-73 closed with the user's own shape — DR-403: neither drafted option; the user named a dedicated cover menu in the reader's top strip plus a context-menu picker in the main window.)*
*Two surfaces, one mechanism. **Reader**: the chrome strip gains a dedicated cover menu — a new control joining the right-end control cluster on every platform (the same edge the app menu and the reader settings control keep; on macOS the whole chrome moves per UI-07 MODIFIED §3.7 and the cover menu moves with its cluster). In the PDF reader its items are "Set this page as cover" (the page currently shown) and "Automatic cover"; in the EPUB reader, "Choose cover…" (opens the image grid) and "Automatic cover". **Library**: the document context menu (row, card) gains "Update cover…", which opens the cover picker: for a PDF, a lazily filled strip of page thumbnails (small renders streamed in as the strip scrolls — the existing page-render path at picker size, background, nothing blocks); for an EPUB, a grid of the book's embedded images in the order they are displayed in the book — reading order first, then the order inside each document; declared images the book does not display follow (DR-411) — served through the existing book-image path; both carry "Automatic cover". The picker is a toolbar dialog (revised 2026-11-19 by the user's Phase-B direction, DR-408): its title sits on a toolbar bar at the top of the dialog — the app's own toolbar language — and every action is a button on that bar; its tiles highlight on hover in the current theme's accent language. The bar is pinned (revised 2026-11-19 by the user's second Phase-B direction, DR-410): the dialog's scrolling belongs to the content area below the bar and the scrollbar never runs alongside it, and the dialog's width fits an exact number of tile columns — the thumbnail rows fill it with no dead space left over. The content area's scrollbar sits at the dialog's edge, as in every other dialog, and stops above the dialog's rounded bottom corners (revised 2026-11-19 by the user's third and fourth Phase-B directions, DR-411 + DR-412). A pick sets the choice; the card updates through the existing cover-appearance mechanism (the glyph until the render lands, then the chosen cover). No cover-management screen; the commands validate and return — the rendering is pipeline work.*

**NFR-12 (CI/release pipeline run-time and cache reuse)** — **new**. *(OQ-71 closed as A — DR-399: a new line, as drafted; NFR-10/NFR-11 stay frozen.)*
*The repository's CI and release pipelines reuse warm caches across runs and across the two workflows: the Linux dependency step is cached against the dependency list so a cold runner pays it once; the Rust build cache is shared between `ci.yml` and `release.yml` so a recent `master` push warms what a tag build consumes; the pnpm store cache keyed by the lockfile stays as verified already in place (M8). The run-time contract is measured, not asserted — the AC-158 wall-clock reporting is the instrument: the release run's Linux job at or below **≈ 400 s** against the 1 380 s measured 2026-11-18 (same machine class; §3.1 M9's warm-build floor is the floor). The hosted macOS runner queue is out of scope (operational, ROADMAP §4).*

**FR-27 (Product identity) — MODIFIED 2026-11-19 (the D33 fix; the user's chosen value).** Released text, quoted for the record (SPEC-v0.0.11.md §2, frozen): *"The app identifier becomes `com.bookkeeper.app`; the app opens its data directory directly under the new identifier — no migration step."*
*New text (change limited to the identifier value; everything else in FR-27 stands — the name, the internal rename, the unchanged behavior): the app identifier becomes **`com.bookkeeper`**; the app opens its data directory directly under the new identifier — no migration step (the user's decision 2026-11-19: fresh start accepted; precedent DR-381). This change also lands the app ahead of a possible future upstream rule.*

**FR-32 (Delete all tags)** — **new** (the user's direction of 2026-11-19: "add delete all tags action in toolbar of tags dialog").
*The tags manager offers one action that removes every tag at once. The action requires confirmation. On confirmation all tag rows are removed and their membership is detached from every document (the schema's cascade); the documents themselves and all their other data are untouched. The action is unavailable while the library has no tags. The count of deleted tags is reported through the app's normal completion feedback. An active filter that referenced a deleted tag drops it — the rule the single-tag delete already follows, applied to the whole set.*

- **Storage — settings keys, as the ROADMAP line names.** Keys `reader.pos.<id>` with a compact JSON value: PDF `{"p":<1-based page>,"o":<0–1 offset fraction within the page>}`; EPUB `{"c":<1-based spine index>,"o":<0–1 fraction within the chapter>}` (OQ-72 closed as A, OQ-69 closed as A — DR-399: the value shapes below are confirmed).

## 2. Requirements

**FR-25 (App updates)** — **MODIFIED** (the presentation, the Skip decision, and the macOS/Linux completion; the check, the source, the signature and the Windows install flow stand).
Old text (RELEASED, `SPEC-v0.0.10.md` §2, verbatim): *"The app maintains itself up to date. On startup the app checks silently in the background whether a newer published version exists: the check never delays a window opening, never blocks any interaction, and asks nothing of the user when the app is current or the source is unreachable. The main window's Settings menu carries a **Check for updates** action that runs the same check on demand and always reports its result. When an update is found the app presents it — the new version and the release notes — and offers to install it: the app downloads the update with visible progress, verifies its signature, installs it through the platform installer, and the app exits for the installation. The update source is the app's GitHub Releases update manifest (`dong-nz/pdf-keeper`, the signed `latest.json`); signing and publishing are the maintainer's release process (§3.11), not app features. No reader window carries update controls — the update is app-global, acted on from the main window."* (The repository name in the source clause is `dong-nz/book-keeper` since the v0.0.11 rename, FR-27.)
New text: *"The app maintains itself up to date. On startup the app checks silently in the background whether a newer published version exists: the check never delays a window opening, never blocks any interaction, and asks nothing of the user when the app is current, when the source is unreachable, or when the user has chosen to skip that version. The main window's Settings menu carries a **Check for updates** action that runs the same check on demand and always reports its result. When an update is found the app presents it in its own **update modal** (UI-56): the current version, the new version, the release notes, and the choices **Install** and **Skip this version**. A manual check that finds the app current reports exactly that. A manual check whose update source is unreachable surfaces a typed error as a toast. The update source is the app's GitHub Releases update manifest (`dong-nz/book-keeper`, the signed `latest.json`); signing and publishing are the maintainer's release process, not app features. The update modal and the download progress are not rendered on reader windows by the startup check; a manual check presents them in the window it was run from (UI-52, UI-50)."*

### 3.2 Update modal and version-scoped Skip (FR-25, UI-52 MODIFIED, UI-56, settings key)

- **`ui/src/lib/updates.ts` rewritten:** `armAvailability` no longer builds a toast; it arms the **update modal** — a Svelte store (`updateOffer.svelte.ts` in `lib/state/`) holding `{ currentVersion, newVersion, notes }` or null; `UpdateModal.svelte` renders from it and is mounted in **both** window roots — `App.svelte` (main) and `ReaderApp.svelte` (the reader manual path, UI-52/AC-149). The store is per-window like every other window state: a check in one window arms only that window. The `Update` resource keeps the close-on-replace discipline the current module already implements.
- **Notes source:** the modal reads the manifest notes through `update.body` — the plugin forwards the manifest `notes` field as `body` (F8; `updates.ts` already reads `update.body` today). There is no second field the UI could read (OQ-74's closed shape, §5).
- **Startup respect of the Skip:** `checkForUpdates(false)` compares `update.version` against the settings value `update_skipped_version`; **equal → nothing renders** (the check stays silent) — a plain equality is sufficient because the plugin only reports strictly newer versions (F13). A greater version presents the modal. The read rides the settings store mirror, which is loaded before the startup check by construction (F14). `checkForUpdates(true)` (the menu item, any window) presents the modal whenever an update exists, skipped or not; "up to date" and failure toasts unchanged; the single-flight `checking` guard stays (F14).
- **Skip action:** `app_set_setting("update_skipped_version", version)` through the existing settings path; `service::set_setting` gains the key in `SETTINGS_KEYS` with the value validated as a semver string (`x.y.z`) — the released validation shape for enumerated values (F6). A newer release overwrites the value when skipped again; no clear action is offered (a stale skip is harmless: it only silences that exact version).
- **Session deferral:** Escape/close on the modal clears the armed offer for the session; nothing is persisted.
- **`UpdateModal.svelte`:** built on `Modal.svelte` (released dialog rules: focus trap, Esc, overlay close — the deferral above); the version line renders `currentVersion → newVersion` from `app_about` (F7) and `update.version`; the notes block per OQ-74; two buttons — *Install* (primary, runs the existing `installUpdate` flow) and *Skip this version* (secondary). i18n keys `updates.modal.*` (the released i18n rule; the version strings are not translated).

### 3.3 Completion and self-restart on macOS/Linux (FR-25, UI-52, new dependency)

- **Dependency (approved by the user's answer, DR-418):** `tauri-plugin-process = "2"` (Rust, pinned to the Tauri 2.12.5 line's current 2.x) + `@tauri-apps/plugin-process` (JS); `tauri_plugin_process::init()` joins the plugin builder in `lib.rs`; capability `process:allow-restart` is added to **both** capability files — `default.json` (main) **and** `reader-windows.json` (the permission is named for the plugin's `restart` command, which the JS client's `relaunch()` invokes — verified against the plugin 2.4.0 permission set, DR-423): the manual check may run and complete in a reader window (UI-52, AC-149), and capabilities are per-window; a relaunch invoked from the reader window would otherwise be denied. The plugin's `relaunch()` terminates the app and starts the installed binary again.
- **Flow (OQ-75 closed as A, DR-422):** in `installUpdate`, after `downloadAndInstall` **resolves** — which today only happens on macOS (F3) and Linux (F4); Windows exits the process before returning (F2) — the job-progress bar is cleared, the completion is surfaced through the released toast affordance (*"Update installed — restarting"*), and `relaunch()` is called after a short visible beat (~1.5 s) so the user sees what happened before the windows close. The reader-window manual path (UI-52) closes with the app on relaunch — stated behavior.
- **Linux scope (OQ-76):** the manifest offers the AppImage (F4); the in-app update is scoped to the AppImage run shape; a `.deb`-installed app documents its update path in the guide (OQ-76's answer decides the wording). This is the shipped reality, recorded honestly, not a new capability.

### 3.4 Status-bar version label (UI-15 MODIFIED, UI-57)

- `App.svelte` main-window init calls `appAbout()` once (the client already mirrors the command, F7); the value lives in a small module store (`appinfo.svelte.ts` in `lib/state/`), never re-fetched. `StatusBar.svelte` renders it in the existing `.spacer`-right position: the version span is the last element; the conditional result-count span keeps its place immediately before it. Style: `--text-12`, `--text-tertiary`, `tabular-nums` (the released count style). No i18n text (a bare version string). Reader windows do not render it (their status surface is separate).

### 3.5 Windows update location (D36 — decision, documentation only)

- No product code changes: the per-user location is the installer default and the update path already keeps it once the app was installed per-user (F5 — `RestorePreviousInstallLocation` finds the HKCU entry). The user's machine needs the one-time removal of the Program Files entry (*Apps & features → Book Keeper → Uninstall* — the old entry is the stale one; the app data is shared either way).
- `docs/release/features/keeping-the-app-updated.md` gains the facts: where the app installs, why an update stays there, and the one-time cleanup note for machines that carry an older per-machine install. The Ship release-notes page carries the same plainly.

### 3.6 macOS drag-strip double-click (D35)

- The app supplies what Tauri's macOS branch cannot (F11), **without competing with it** (F15): a small shared action `dragStrip` (`lib/dragstrip.ts`, a small window-surface module beside `platform.ts` — the released `lib/actions.ts` is the §5.3.10 UiAction-definition module and a mount action does not belong there; the placement is recorded as DR-424) applied to the two drag surfaces (`Toolbar.svelte`, `ReaderApp.svelte`). On **macOS only** (`platform.ts`, F10): the `data-tauri-drag-region` attribute is **not rendered** (the built-in `drag.js` then does nothing on the strip) and the action owns the strip — `mousedown` with `detail === 1` calls `getCurrentWindow().startDragging()` (the same call the built-in makes), `detail === 2` calls `getCurrentWindow().toggleMaximize()`. Both permissions already exist in both capability files (F12). No double toggle is possible: the built-in branch is structurally absent on macOS surfaces…
- On Windows/Linux the action attaches nothing and the attribute renders unchanged — the built-in `drag.js` behavior is the released path and stays untouched. `flowWindowChrome` keeps its released Windows assertions (double-click maximize via the built-in path; the app's handler is inert — unit-tested through the platform gate).
- Verification note (Phase B, the user's hardware): single-press dragging on the macOS strips must feel unchanged (AC-191's observation half); the released `"false"` overrides on interactive children are untouched (F15) — the action binds only presses the browser attributes to the strip element itself.

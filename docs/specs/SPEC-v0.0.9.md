## 0. Scope and versioning

**What this release is.** EPUB support end-to-end, as extended by the user's decision of 2026-11-10 (DR-262 — the roadmap's Phase 1/Phase 2 split is merged into this release): **EPUB documents become first-class library members** — import, metadata, cover, OS-application open, and every existing library capability (tags, favorites, Reading, search, rename, relink, missing detection, bulk operations, Details) applies to them exactly as to PDFs — **and the app reads EPUBs inside itself**: a dedicated reader window for reflowable EPUB content (FR-23). The technical approach for the reading half — who lays out the book — is **decided (OQ-57 closed → A, DR-294): the bundled web engine displays, Rust parses and serves** (design §3.9, options and trade-offs recorded there).

**What this release is not (out of scope):**
- **Full-text search** (out of scope since v0.0.1; applies to EPUB content the same way as to PDF text).
- **EPUB encryption and DRM** (the FR-20 password concept is a PDF fact; a DRM-encumbered EPUB opens with the OS application — the app does not license a DRM engine).
- **Page numbers / pagination facts** (EPUB has no stable pages; the library never shows page facts).
- Paginated page-turn mode and facing spreads — **OQ-57 closed → A (DR-294)**: deferred to a later release (§3.11).

**Version bump (0.0.8 → 0.0.9, minor on the 0.x line):** a new document type managed by the library, and a new reading surface for it. The user's request named the version; the bump matches the roadmap's line 2. Agent proposes nothing about the number — the user set it.

**ID policy:** consumes `FR-22` (EPUB library support) and `FR-23` (in-app EPUB reader) — **the app-updates reservation moves a fifth time (OQ-52 closed → A, DR-294)**; the reservation returns at `FR-24`+; the fourth move was v0.0.8's closed OQ-46, per DR-264. New items are binding once the release is approved. All are **PROPOSED**.

**FR-22 (EPUB library support)** — **new** (consumes `FR-22` per OQ-52 closed → A):
*The app manages EPUB documents in the same library as PDF documents. Importing `.epub` files — through the file picker, folder import, and drag-and-drop — registers them as library documents; the document's facts are read from the EPUB package itself: title and author from its published metadata, cover from the cover image the package declares (a package that declares none, or whose cover cannot be decoded, uses the released glyph fallback). The released title-fallback rule (filename when metadata is absent or unusable) applies unchanged. Every library capability applies to EPUB documents exactly as to PDF documents: tags, favorites, the Reading collection, search, rename, relink, missing detection, bulk operations, Details, the status bar. Reading an EPUB happens in the app's own reader (FR-23); opening with the OS default application remains available as an explicit action (activation semantics per OQ-54 closed → A). The password concept (FR-20) is a PDF fact and never applies to EPUB.*

**FR-23 (In-app EPUB reader)** — **new** (consumes `FR-23` per OQ-52 closed → A; OQ-57/OQ-58 closed → A — the invariant core below **and** the option-A surface it names are the requirement):
*The app displays and reads EPUB documents inside itself: opening an EPUB shows its content in a dedicated reader window (one window per document — the released FR-17 window pattern), navigable through the whole book by table of contents and by flow, with reading typography the app controls (at minimum text size) [OQ-57 closed → A: continuous flow in the app's typography]. Reading an EPUB does not require an external application. Opening with the OS default application remains available as an explicit action. A document whose file is missing, or a package the app cannot render, never opens silently: the typed error paths of FR-08 apply, and an unrenderable file additionally offers the OS-application open. The Reading-collection semantics (v0.0.8 FR-19: manual-only membership) are untouched.*

### 3.2 EPUB metadata module — `src-tauri/src/epubmeta/`

- The library import pipeline branches on the lowercased extension: `.pdf` → `pdfmeta` (untouched); `.epub` → `epubmeta::extract(path) -> Result<EpubMeta, AppError>` with `EpubMeta { title: Option<String>, author: Option<String>, cover: Option<CoverRef> }` — **`CoverRef` is the declared cover's package entry path + declared media type** (resolved through the same `container.xml` → OPF read the metadata needs — no extra parse), **not decoded bytes**: the released pipeline generates covers asynchronously in the cover queue (§3.3), and the two-phase rule says import reads facts, the worker decides pixels. **Two-phase parse (performance rule, §3.12):** `extract()` reads only the import-needed facts; spine/nav/reading structures parse on first open, never at import.
- Read order: open the zip → validate the `mimetype` entry → parse `META-INF/container.xml` (rootfile path) → parse the OPF: first `dc:title` → title, first `dc:creator` → author (name-order variants taken as-is, like the released author rule), `meta name="cover"` → manifest id → item href → **cover reference (`CoverRef`, §3.2 — entry path + declared media type; the bytes are read by the cover worker, §3.3)**. **Href resolution rule**: manifest/spine hrefs are relative to the **OPF document's own directory**, URL-percent-encoded, and occasionally use backslash separators (real-world packages break here): resolve against the OPF directory → percent-decode → normalize backslashes → zip lookup; a failed lookup follows M17. A per-entry decompressed-size guard bounds zip-bomb input; a breach follows the M17 rule.
- **Malformed EPUB** (unreadable zip, missing container, missing/unparseable OPF): the released rule M17 applies unchanged — the document imports with the filename-title fallback and the glyph cover; the typed error surfaces only if the app is asked to do something the file cannot support. No silent failure, no import abort.
- **No schema change**: the document's type is its extension (`documents.filename` carries it). No `doc_type` column — a derived fact stays derived (R2.1 minimalism). FR-21's rename semantics in a two-type library are the user's decision of 2026-11-10 (DR-285; §2 FR-21 MODIFIED): a rename between supported extensions (`.pdf` ↔ `.epub`) is accepted and the document behaves as its new type — the type derivation is re-run on rename (title re-derivation only when `title_source = auto`, under the new type's rules; cover re-enqueue under the new type's parser, reusing the re-key the released rename already performs); a new name whose extension is outside the supported set is rejected with the typed error and nothing changes. AC-124 tests the rule. No new whitelisted commands for the library half: import, metadata, and cover all happen inside the existing import pipeline (R1.1); the frontend changes for FR-22/UI-46 are filters and labels. The reading half's content delivery is decided — **OQ-58 closed → A**: the custom protocol (§3.10).
- Dependency: **OQ-53 closed → A (DR-294)** — `zip` + `quick-xml` approved (the user's answer is the AGENTS §2 approval); the crates enter `Cargo.toml` at implementation start.

### 3.3 Covers (FR-22, existing pipeline)

- **Cover worker dispatch (named, reviewed 2026-11-11, DR-293).** The released cover worker is a client of the single pdfium owner — `RenderService` (M23): a cover is page 1 rendered at the cover pipeline's fixed target. **pdfium cannot open an EPUB**, so the worker branches on the extension: `.pdf` → the RenderService path, untouched; `.epub` → open the zip, resolve the declared cover through the §3.2 `CoverRef` path (container.xml + OPF only), read that entry, decode with the `image` crate, composite per the rule below; any failure (no declared cover, undecodable entry, malformed package) → the released glyph fallback. The queue, the DR-113 cache key, the interactive-beats-background priority rule, and regeneration on relink/rename are unchanged.

- A declared cover item whose media type is raster (JPEG/PNG as declared in the OPF manifest): decode with the existing `image` crate, composite onto the released cover canvas with **contain-fit** — the image is scaled to fit the A4-ratio frame with its aspect preserved, letterboxed on a **transparent** ground (DR-299: the canvas is RGBA, the bars show the card surface in the current theme); **never cropped** (an EPUB cover is arbitrary-shaped; cropping silently loses text on jacket covers). Then the released pipeline unchanged: 640 px output, the DR-113 cache key (path + mtime + width).
- No declared cover, an SVG/non-decodable cover this release, or a malformed EPUB: the released glyph fallback.
- Cover regeneration on relink/rename follows the released rules (cache key changes with the path/mtime).

### 3.9 In-app EPUB reading — chosen design (OQ-57 closed → A; options B/C recorded in §5)

The problem, precisely: an EPUB is reflowable HTML/CSS in a zip. The PDF reader works because pdfium is a native layout engine — Rust lays out each page, renders a PNG, the frontend displays images (the released FR-17 design). No such engine exists in our stack for EPUB (pdfium reads PDF only, M19). But the product already carries a full HTML/CSS layout engine in every window: WebView2/Chromium (M20). The options differ on **who lays out the book** — the bundled web engine, with Rust serving it content, or Rust itself.

**Option A — app-owned reader: Rust parses and serves, the web engine displays, continuous flow, app typography.** *(the agent's recommendation)*
How it works: `epubmeta` (§3.2, already needed for import) gains the reading facts — spine order, manifest, chapter resources; the reader window (the released one-window-per-document pattern) renders sanitized chapter XHTML in the app's own reading typography (font family/size/line width/spacing chosen by the design system); a TOC panel from the package's table of contents (nav → NCX → spine-derived, consequence 1 below; the released UI-33 control pattern); progress = book position (spine position + scroll fraction); navigation = continuous flow through the spine.
- *Pros:* no new frontend dependency; **one parser** — the same Rust code reads the package for import, covers, and reading (R1.1 intact: all product logic in Rust; the web engine only *displays* HTML, the same category as every other surface of this UI); typography and themes fully under app control — a dark reading mode that matches the design system; text selection and copy come free (the roadmap's reader-completion item arrives for EPUB at no extra cost); a simple, stable progress model (no CFI machinery); robust by construction — author scripts disabled, author CSS restricted to a safe subset.
- *Cons:* no paginated page-turn mode in this release — continuous flow only (a named scope limit; the PDF reader also ships a continuous mode); the reading surface is our own code (bounded effort: the window pattern and the TOC control pattern already exist); author-CSS edge cases are ours to normalize (embedded fonts work through the protocol; fixed-width layouts get width-normalized).

**Option B — epub.js in the reader window: Rust serves the package, a mature frontend library renders it.**
- *Pros:* the book-like experience arrives built-in: paginated page turns and spreads, reflow done by a mature engine, TOC and CFI-based progress; the Rust side is only the content server; the fastest path to a complete reading experience.
- *Cons:* a new **frontend** dependency (package.json — AGENTS §2 approval; `epub.js` is effectively single-maintainer); **a second parser** — epub.js parses the package itself, duplicating the Rust parser import and covers still need (two implementations of EPUB semantics, two failure modes — tension with R1.4); an **explicit R1.1 exception** — parsing and pagination are product logic living in JavaScript (a Rule-7 decision); theming fights author CSS (dark reading mode possible but fiddly); text selection across its paginated iframes is inconsistent.

**Option C — Rust layout engine: EPUB laid out in Rust, pages rendered to images, the PDF reader pipeline reused.**
- *Pros:* architecturally identical to FR-17 — R1.1 pure; the released view modes and zoom model apply; no frontend dependency.
- *Cons:* implementing HTML/CSS layout in Rust (block and inline flow, floats, tables, images, `@font-face`, the author-CSS subset real books use) is a months-long engine project with an unbounded defect surface; rendering quality on real-world EPUBs is doubtful at first-release scope; no text selection. The purity is real; so is the cost.
- *(Variant D — Rust converts EPUB to PDF and reuses pdfium — rejected with C: it needs the same layout engine, and fixed pages lose reflow, which is the point of EPUB.)*

**Reading-model consequence of the choice.** A ships continuous reading with app typography and free text selection; B ships page turns under third-party constraints; C ships page images without selection. These are different reading products, not implementation flavors — OQ-57 is the release's central decision.

**Design consequences if A is chosen (binding on UI-48 and the §3.9/§3.10 text as drafted; recorded 2026-11-10, DR-285):**
1. **ToC source order**: EPUB3 **nav element** (manifest item with `properties` containing `nav`) → EPUB2 **NCX** (`navMap`) → spine-derived fallback. The spine is reading order, not a table of contents; the draft's "fed by the package spine" is corrected. The released `OutlineEntry` shape maps cleanly: depth from the nav tree, position to spine items.
2. **Sanitization mechanism**: chapter documents are XHTML — well-formed XML, so the same `quick-xml` dependency round-trips them: strip `<script>` elements **including scripts inside inline SVG subtrees**, strip `on*` event-handler attributes everywhere (HTML and SVG alike), strip `javascript:` hrefs, and strip `<iframe>`/`<object>`/`<embed>` entirely (a named limitation: in-package frames are rare; the loss is stated, not discovered); rewrite `src`/`href`/`xlink:href` to the §3.10 URLs (resolved by the §3.2 href rule), and **rewrite `data:` URIs to §3.10 protocol entries** — the released CSP's `img-src` does not admit `data:` (verified: `tauri.conf.json` line 24), so inlined images/fonts that pass unrewritten would silently fail, exactly the DR-277 class of CSP surprise; keeping the CSP tight beats widening it. Keep inline `style`. Author scripts are off by construction **and** enforced again by the CSP — the released CSP carries no `script-src`, so scripts fall back to `default-src 'self'` without `'unsafe-inline'`: inline scripts, event-handler attributes, `javascript:` URLs, and remote-origin scripts are refused execution in every window today. Sanitize is the first layer; the CSP is the second; neither alone is relied on.
3. **Author CSS**: kept as linked stylesheets, but the app's reading stylesheet is injected **after** the author's with `!important` on the typography properties (font family, size, line-height, measure, colors) — author layout intent (indents, margins, image sizing) survives; app typography wins. Embedded fonts arrive through the §3.10 protocol (author `@font-face` hrefs rewritten like every other href).
4. **Fixed-layout books** (children's books, comics): rendered as width-normalized continuous blocks — a **named limitation** of this release, recorded in the guide and the release notes, not silence.
5. **RTL books**: the author's `dir`/`direction` pass through — free with continuous flow.
6. **Text size** is a global reading setting persisted in `settings` (typography, like the theme) — the PDF reader's session-only zoom has no EPUB analogue and none is invented.
7. **Reading position is not persisted this release** (consistent with FR-19's manual-only Reading and the roadmap's progress deferral) — stated explicitly so no one builds it by accident.
8. **The reader command surface (R1.3 — the whitelist, added by review 2026-11-11, DR-293).** The EPUB reader needs exactly **one new whitelisted command**: `app_epub_manifest(id)` → the reading manifest: spine items (package entry paths, media types, **uncompressed entry sizes** for the §3.13 position model), the ToC tree in the released `OutlineEntry` shape (source order per consequence 1), the package's declared direction/language, and the §3.10 protocol base URL. Chapters, images, CSS and fonts then arrive **through the protocol** (OQ-58 closed → A) — no per-page commands; only if the §3.10 probe fails and option B is taken as its fallback (DR-294) does an `app_epub_resource(id, path)` bytes command replace the protocol (§3.10 B plumbing). Mirror in the single typed client (`api.ts`, R1.3); the guard is the released typed resolution — the same `document_not_found` / `missing_file` path `app_open_reader_window` uses. **Window creation reuses `app_open_reader_window` unchanged** (M23: verified type-agnostic — it resolves the row and file and builds `index.html?reader=<id>` with no extension gate); the frontend branches on extension before any reader-store work (§3.5), so no PDF reader store is ever created for an EPUB and vice versa.

### 3.10 Content delivery (OQ-58 closed → A — option A is the chosen mechanism; B/C recorded in §5)

- **A. Custom URI-scheme protocol (recommended).** `Builder::register_uri_scheme_protocol` exists in the bundled Tauri 2.12.5 (verified, M18): a Rust handler serves zip entries on demand as `pdfkeeper-epub://<document-id>/<package-path>` — the web engine gets ordinary URLs for chapters, images, CSS, embedded fonts; no IPC payload bloat; nothing extracted to disk (the reference-in-place principle holds). **Precedent (M21, verified 2026-11-10): the product already serves every cover image and every reader page through Tauri's built-in asset scheme on this exact WebView2 build** — custom-scheme serving is proven in-product infrastructure. What an **app-defined** scheme must still prove is a probe run **after approval, as the first build step before any reader code** (the user's decision of 2026-11-10, DR-285): the async handler streaming a zip entry as a `Response`; `fetch()`/XHR from the reader window to the scheme (CORS); and the **CSP edits the design must carry** — `img-src`/`style-src`/`font-src`/`connect-src` gaining `pdfkeeper-epub:` (the DR-277 finding — the CSP silently blocking plugin IPC — is why this is design text, not a runtime discovery). If the probe fails, the deviation follows Rule 7 and option B becomes the fallback. **Namespace rule (design, not implementation detail):** the handler resolves a request as a key into the **archive's central directory** — no filesystem path is ever constructed from a hostile entry name, and the §3.2 normalization stays inside the archive namespace (a `../` can never escape the package). **Probe checklist item (privilege boundary):** verify empirically that a page script served from the content scheme cannot reach the whitelisted commands (Tauri's capabilities gate IPC by origin — the app origin is `tauri.localhost`-class, content pages are the book scheme's origin); the design relies on this boundary as the third layer. **Probe checklist item (cache):** whether WebView2 caches app-defined-scheme responses served with `Cache-Control`/ETag headers (§3.12 rule 5) — if it does not, the §3.12 sanitized-bytes LRU carries the repeat-read cost instead.
  - **Probe ran 2026-11-11 (DR-297): option A is confirmed on this build; the checklist is closed and three corrections bind the commands stage.** (1) **Windows URL shape:** wry serves an app-defined scheme to the web engine through the origin workaround `http://pdfkeeper-epub.localhost` — the same mechanism behind the released `http://asset.localhost` (M21) — while the Rust handler receives the original scheme URI; the frontend base URL, the manifest command's base-URL field, and the CSP therefore use the `http://pdfkeeper-epub.localhost` form, keeping the bare `pdfkeeper-epub:` CSP form for non-Windows webviews (the released CSP's `asset: http://asset.localhost` two-form pattern). (2) **The engine does not cache** app-defined-scheme responses: the handler's hit counter proves every repeat load re-requests despite `Cache-Control`/ETag — §3.12 rule 5's documented fallback branch applies (the rule-4 LRU carries repeat reads; the headers are still served). (3) **The IPC boundary does not gate content origins:** a script served from the content scheme reached `tags_list` (Tauri treats `*.localhost` as local) — the "third layer" reliance above is retired; the reading surface's defense is the sanitizer (primary, AC-137) plus the CSP, and **book documents are never mounted as frames or documents** — chapters are fetched and inlined as sanitized DOM, so a content-origin script never runs at all. `frame-src` was probe scaffolding only and is not carried; the CSP carries `img-src`/`style-src`/`font-src`/`connect-src` extended with both URL forms. The fallback to option B is not needed.
- B. Commands returning resource bytes: works with today's command plumbing; base64 images through IPC are heavy; acceptable for text, poor for assets.
- C. Temporary extraction to a cache directory: the simplest URLs, but it breaks reference-in-place and adds a cache lifecycle. Weaker.

### 3.12 Reading performance posture (recorded 2026-11-11, DR-287)

**Baseline fact that frames everything:** the EPUB reading path carries **no rasterization** — no pdfium layout, no page→PNG encode, no page-image cache. The dominant cost of PDF reading was the PNG encode (~90 % of measured page CPU, the v0.0.7 measurements, DR-174/175); EPUB reading has none of it. The posture's job is to keep every cost **bounded per chapter, never per book**.

**Design rules (binding on option A):**

1. **Two-phase parse** (§3.2): import reads only what import needs (mimetype → container → OPF metadata + cover); spine/nav/reading facts parse **on first open**. Import never pays for reading structures (protects the AC-131 budget).
2. **Streaming parse, never DOM**: quick-xml event reader/writer for OPF parsing and chapter sanitization — O(1) memory in document size; early-stop (`skip`) once the needed fields are found. Some real books carry 1 MB+ manifests; parse cost stays flat.
3. **Bounded DOM (the largest lever)**: the continuous-flow view mounts only the visible and adjacent spine items (IntersectionObserver mount/recycle — the released windowing philosophy applied to chapters); a single huge chapter mounts in chunks as it scrolls. DOM size is O(3 chapters), never O(book).
4. **Sanitized-bytes LRU**: the protocol handler's sanitized output is cached in a bounded in-memory LRU keyed (doc-id, entry, mtime) — the DR-113 key discipline, invalidation following rename/relink — so back/forward navigation never re-sanitizes.
5. **Cache headers**: served entries carry `Cache-Control`/ETag (doc-id + file mtime) so repeat asset requests (images, CSS, fonts) are answered from cache rather than re-served; whether WebView2 caches app-defined-scheme responses is a **probe item** (§3.10). *Measured 2026-11-11 (DR-297): it does not — every repeat load re-requests the handler. The rule-4 LRU carries the repeat-read cost (the documented fallback branch); the headers are still served.*

**Build-stage optimizations (no design status — apply, then measure):** prefetch + idle-time sanitize of the next spine item; the sanitizer adds `loading="lazy"` to `<img>`; scaled JPEG cover decode via `image`'s `ImageReader::into_scaled_dimensions` (1/2–1/8 DCT scaling; verify the API shape at build); STORED zip entries served without decompression.

**Rejected, with reasons:** pre-sanitizing the whole book to a disk cache (a CPU spike at the worst moment, a cache lifecycle, breaks reference-in-place); CFI/pagination machinery (option B's machinery); font subsetting and image transcoding (the webview cache plus rule 5 already cover it).

**Measured-budget discipline (the NFR-09 pattern, guard `AC-138`):** before the reading code is written, numeric budgets are defined and recorded in the Decision Log — first-paint on the 1 MB-chapter fixture, smooth continuous scroll on the 500-chapter fixture (the harness pattern of the released reader-performance flows), and a reader-window memory ceiling measured against the debug binary via CDP probes (the v0.0.7 DR-174/175 method). Optimizations are claimed only with measurement; the stress fixtures come from the §3.8 generator (same templates, scaled).

### 3.13 The reading surface — concrete design (UI-48, **binding** design: OQ-57/OQ-58 closed → A, DR-294; recorded 2026-11-11, DR-288)

The surface deliberately mirrors the released reader (FR-17 window pattern, UI-30 strip, UI-33 ToC, UI-13 icon-only controls with tooltips, UI-09 toggle states, the reader-store single-source rule DR-155) with page semantics replaced by flow semantics. Concrete, so it is reviewable and testable; the typography **values** below are the agent's proposal and are adjustable at approval — the structure is not.

**Window.** The released one-window-per-document reader window (title = document title, released window controls); the `?reader=<id>` route branches on extension before window creation (§3.5). No new window kind.

**Content surface — one mode: continuous vertical flow in spine order.**
- **Chapter boundaries:** a chapter header line (label from the ToC entry, else the document's own first heading, else none — content only), then the chapter. Scrolling down mounts the next spine item, scrolling up mounts the previous — the mount window reuses the released `$lib/virtual` windowing mechanism (the same machinery as the PDF continuous mode) with the §3.12 rule-3 bound; a huge chapter mounts in slices as it scrolls.
- **First paint:** the first spine item is fetched and mounted before the window paints — the released current-page-first rule (ReaderView precedent), never "window first, content later"; while the first item is in flight the window shows the released loading surface, and a not-yet-mounted chapter appears only as its header line at the edge of the mount window.
- **Reading column:** centered, max measure **68 ch**, UI-19 gutters; ground and text colors from the active theme ramp — a dark reading mode is the theme, not a per-window setting.
- **Typography tokens (proposed values):** body stack `"Iowan Old Style", "Palatino Linotype", Palatino, Georgia, serif` (system fallback); line-height **1.6**; left-aligned (justification off — rivers); size ladder **[14, 16, 18, 20, 24, 28] px**, default **18**; persisted globally in `settings` (§3.9 consequence 6); RTL books pass the author's `dir` through (§3.9 consequence 5).
- **Images:** inline, `max-width: 100%` of the column, height auto, centered; `loading="lazy"` added by the sanitizer (§3.12).
- **Links:** internal anchors **jump within the book** — href → manifest id → spine item; an unmounted target mounts first, then the view scrolls to the element id (footnote links and their back-links work as content provides them). External `http(s)` links open with the OS default browser via the already-bundled opener plugin (`open_url`; a capability extension in the UI-40 pattern, recorded per R9.1 before code). Context menu stays suppressed (the D20 rule); selection and copy are native (`Ctrl+C`).
- **Fixed-layout books:** width-normalized continuous blocks — the §3.9 consequence 4 named limitation, visible as such (no fake pagination).

**Bottom control strip (UI-30 surface), control order fixed:**
1. **ToC control** — present only when the package has a ToC, positioned first when present (the released DR-207 rule); opens the released side-panel pattern (UI-33/TocPanel, same anchor and focus behavior) fed by nav → NCX → spine-derived (§3.9): nested entries with the released initial collapse state, the **current entry highlighted from the store's scroll source** (the released current-entry derivation), entries jump via the same resolution as internal links.
2. **Position control** — replaces the page field: readout `NN % · <chapter label>` derived from the store's single scroll source (the DR-155 single-source rule, never a relayed copy). **Position model:** book percent from **cumulative uncompressed spine-entry sizes read from the zip central directory** — sizes the archive already carries, no parsing, computed once at open and held in the reader store; the live readout interpolates within the current chapter's scroll range (chapter start → chapter end maps the chapter's slice of the percent). Clicking the readout opens a **jump field** — type a percent, Enter/blur resolves to the spine item containing that percent and lands at its start (the released page-field editing rule, typing owns the field while editing). A book with no ToC still jumps by percent — the model works on the spine alone.
3. **Text-size control** — the zoom control's pattern (DR-221): − / + step the ladder, the current step named in the trigger; the change applies **live** (a reading CSS custom property; reflow is the browser's), and the chosen step persists globally in `settings` (§3.9 consequence 6).
No view-mode control (one mode — nothing to toggle), no zoom control, no prev/next page buttons.

**Keyboard map (mirrors the released reader map, UI-39 semantics, page → flow):** `ArrowUp`/`ArrowDown` one notch; `PgUp`/`PgDn` one viewport; `Home`/`End` book start/end; `Escape` closes the window (released rule); the ToC panel follows the released TocPanel focus/Escape behavior. No new letters beyond the released set.

**Focus and compliance:** the window follows the released focus rules (UI-06: strip controls reachable in order, the panel behaves as the released panels do); strip controls carry the released toggle/pressed states (UI-09) and tooltips (UI-13); every string — labels, tooltips, readout, error paths — goes through i18n (R4), including the percent readout format.

**Error and empty states:** malformed/unrenderable book → the released unrenderable-document path (typed message + **Open with the default app** action — AC-133); missing file → the released missing-document rules; no ToC in the package → the ToC control is absent (the present-when-present rule), flow navigation still reaches the whole book through the spine.

**What the surface does not have, stated so nobody builds it by accident:** zoom/fit controls, page numbers or page fields, in-window text search (full-text is out of scope), annotations/highlights (the roadmap's reader-completion item), reading-position persistence (§3.9 consequence 7), page-turns/spreads (§3.11).

**OQ-53 — EPUB parsing dependency (the answer is the dependency approval).**
- **A. `zip` + `quick-xml` (two small crates).** *Recommended — `zip` reads the container (mimetype, cover bytes) and `quick-xml` parses container.xml/OPF with full control over the few fields needed; both are widely used and small; nothing about EPUB semantics is hidden from us. **OQ-57 — the EPUB reading approach: who lays out the book (§3.9).**
- **A. App-owned reader — Rust parses and serves, the web engine displays: continuous flow, app typography.** *Recommended — no new frontend dependency; one parser shared by import, covers, and reading (R1.1 intact); typography and dark reading mode fully under design-system control; text selection and copy come free; progress is a simple stable book position. Cost: no paginated page-turn mode in this release; the reading surface is our own bounded code.*
- B. epub.js in the reader window — paginated page turns and spreads arrive built-in, the fastest path to a book-like experience. Cost: a new frontend dependency (effectively single-maintainer library), a second parser duplicating ours, an explicit R1.1 exception (Rule 7), theming friction with author CSS, inconsistent text selection across its paginated iframes.
- C. A Rust layout engine rendering page images — R1.1 pure, the PDF reader pipeline reused. Cost: months of HTML/CSS layout-engine work with an unbounded defect surface; no text selection. The variant "convert EPUB to PDF and reuse pdfium" is rejected with C (same layout problem; fixed pages lose reflow).
The options are different reading products, not implementation flavors — this is the release's central decision. If page turns matter in the first release, B is the honest answer; A defers them without foreclosing them.

**OQ-58 — content delivery for the reading half (applies to options A and B).**
- **A. Custom URI-scheme protocol `pdfkeeper-epub://`** (§3.10). *Recommended — the registration API is verified present in the bundled Tauri 2.12.5 (M18), and the built-in asset scheme already serves this product's cover images and reader pages on this WebView2 build (M21) — the mechanism is proven in-product. Ordinary URLs for chapters, images, CSS, embedded fonts; no IPC bloat; nothing copied to disk. What an app-defined scheme must still prove (async zip-entry streaming, fetch CORS, the CSP edits, the IPC-origin privilege-boundary check of §3.10, and the webview cache behavior for cache-headered responses of §3.12) is a probe step run after approval, as the first build step (the user's decision of 2026-11-10, DR-285); a failed probe reopens the choice per Rule 7.*
- B. Commands returning resource bytes: works with today's plumbing; heavy for images.
- C. Temporary extraction to a cache directory: the simplest URLs, but it breaks reference-in-place and adds a cache lifecycle.

**OQ-59 — app naming: does the app rename now that EPUBs are managed? (the user's question of 2026-11-10).**

Keep "PDF Keeper" through the 0.x line; revisit when the user declares 1.0.0 (or when the managed content genuinely shifts).** *Recommended — the name stays honest for the dominant format; "ebook-keeper" would misname the PDF-majority library and overclaim the ebook format family (MOBI/AZW3/FB2/DJVU are out of scope); at 0.x there is no distribution pressure; identity re-declaration belongs to 1.0.0, which is the user's act.*

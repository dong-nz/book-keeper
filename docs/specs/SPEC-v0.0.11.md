## 2. Requirements

**FR-26 (Application logging)** — **new** (the user's Phase-B feedback item 6 of 2026-11-17, deferred here by the user's answer closing OQ-61 — option B, v0.0.10 spec DR-339; the request text as recorded there: "an application log that reports problems, with a log-path setting and a level (Info / Error, default Error)").
*The app keeps an application log: a plain text file in the app's own data directory (the same directory that holds the library database and the cover cache — platform-resolved, never a hard-coded path), one event per line: timestamp, level, subsystem, message. Two levels exist: **Error** (default) records every failure the app reports to the user — any command that returned an error — plus the background subsystems' failures (import passes that failed a file, cover-queue render failures, update-check failures, startup and shutdown anomalies); **Info** adds the normal lifecycle — startup and exit, import runs with counts, window opens and closes. The level is a setting (default Error) stored through the released settings store; changing it takes effect immediately, needs no restart. The log never records document *content*, file *contents*, or anything the library already stores — it records application events about files, not the files themselves (privacy line: paths yes, content no). The log file is capped: when it reaches its size cap the current file is renamed to a single `.1` predecessor and a fresh file starts (at most two files on disk at any time). The log file is a plain file the user may open with any text handler; the app itself never shows log content in a window.*

**UI-53 (Settings *Log* section)** — **new**.
*The Settings dialog gains a section **Logs** (the released section pattern of the dialog, UI-12 structure): a level selector with the two levels (Error default, Info) rendered with the released select control, the log file's full path shown read-only, and an **Open log file** action that opens it with the system's default handler (the released opener path). The section is the log's only surface: no in-app log viewer, no "clear log" button (the file is the user's to manage; the cap is the app's only intervention), no new dialog class. A new section is added to the dialog for both the main window and — through the shared dialog component — the reader windows' *Settings…* item (UI-50), with no other change to the dialog.*

**NFR-10 (CI verification pipeline)** — **new**.
*The repository runs its verification on every push and on every pull request, on the repository's CI infrastructure: `cargo test` (all platforms in the build matrix), `cargo clippy -D warnings`, the frontend unit suites (`vitest`), `svelte-check`, and the UI lane runner (`scripts/ui-verify.mjs` full mode, per OQ-64's matrix answer). A failure in any layer fails the pipeline; the pipeline is the same commands the local Phase-C run uses — CI does not define a second verification language (RULES R6's "tests + clippy + real app" keeps its meaning: the lane runner is the real-app layer). The pipeline must not take longer than its usefulness warrants: wall-time is reported per job exactly as the local runner reports it (the timing rows exist; CI reuses them).*

**NFR-11 (Release packaging and publishing pipeline)** — **new**.
*Every tagged release (`v…`) produces, from the tagged commit: the Windows installers (the released nsis/msi), a macOS bundle, and Linux packages per the OQ-65/OQ-64 answers — built on the CI matrix, not on a developer machine; the update artifacts signed with the app's update-signing key (the minisign signature the updater verifies — the `.sig` files the released FR-25 path consumes); and a published GitHub Release carrying the artifacts plus the `latest.json` update manifest with the per-platform entries the released updater reads. From that moment the released app's update check (FR-25) finds the new version on every supported platform with no manual upload step. Pre-release tags (e.g. `vX.Y.Z-rc1`) may publish to a draft release so the pipeline itself is testable before a real release consumes it.*

**NFR-04 (Platforms)** — **unchanged** (AGREED since DR-17; quoted for the record: "Windows 10+, macOS 12+, Linux via AppImage + .deb. Installers built per-platform."). The DR-92 acceptance ("Windows-only packaging with the NFR-04 cross-platform gap accepted as a known limitation") ends with this release; every release note's standing limitation line is removed.

### 3.2 Logging — Rust core (`src-tauri/src/applog/`, new module; R1.1: plain library module, `cargo test`-able without UI)
- **Shape:** a small synchronous writer behind an internal `AppLog` handle owned by the app state: `error(subsystem, message)` and `info(subsystem, message)` methods, each writing one line `RFC3339 UTC timestamp <spaced> LEVEL <spaced> subsystem <spaced> single-line message`. No `log` facade, no async queue: the write is a few hundred bytes appended to an OS file; the volume is bounded by design (errors are rare by definition; Info adds tens of lines per session). Hot-path measurements (page serving, search) are not instrumented — logging sits at the command boundary and subsystem failure points, not inside inner loops.
- **Hook points:** the command boundary (M5) — every `Err(AppError)` returned to a frontend call is logged with its command name and error class (message text as the user would see it); the import pass's per-file failures; the cover queue's render failures; the update-check failures (startup and manual); startup/exit lifecycle lines at Info. No new call-site changes beyond those boundary points.
- **Level:** read from the settings store at each write decision through a cached level flag refreshed on the settings-write path (the settings store already notifies the frontend; the Rust side re-reads on its own settings command — no new notification channel). Default `Error` when no key exists (the released settings default pattern).
- **File and cap:** `<app_data_dir>/logs/app.log`; on write, if the file exceeds **2 MiB**, rename `app.log → app.log.1` (replacing any existing `.1`) and start fresh. Two files maximum; no compression, no timestamps in names (the cap is a safety valve, not an archive).
- **New commands (R1.2 thin wrappers):** `log_level_set(level)` (validates `error|info`, writes through the settings store, updates the cached flag) and `log_open()` (resolves the log file path and opens it through the opener plugin's Rust API — creating an empty log file first if none exists yet, so the action never fails on a clean install). The level *read* goes through the existing settings read path (M6); the *path display* needs the path: `log_open` is the only surface, and the dialog shows the path from a `log_path()` read command — three thin commands total, added to the R1.3 whitelist and the typed client.
- **What logging must not do:** never block a product path on I/O failure (a failed log write is swallowed — the log cannot create the failures it records); never log document content (FR-26's privacy line); never log secrets (no password-prompt values, no update URLs' query parts).

### 3.4 CI pipeline (NFR-10) — shape decided by the user's answers OQ-63 A / OQ-64 A (DR-348)
- **Host (OQ-63 A):** GitHub Actions, free tier for public repos. Two workflows:
  - `ci.yml` — on `push` and `pull_request`: a three-job matrix (`windows-latest`, `macos-latest`, `ubuntu-24.04`): `cargo test`, `cargo clippy -- -D warnings`, `pnpm install && pnpm test` (vitest), `pnpm exec svelte-check`. The **lane runner** (`node scripts/ui-verify.mjs`) runs on the Windows job only (OQ-64 A — the harness is Windows-shaped: WebView2, the fixture build, the timing baselines); Linux jobs install the Tauri Linux deps (`libwebkit2gtk-4.1-dev` et al.) for the Rust build; the lane runner does not run on Linux/macOS in this release.
  - `release.yml` — on tag `v*` (OQ-65 A: no OS-level signing — the workflow builds unsigned bundles): `tauri build` per platform target (M2's list, filtered per OS; Linux targets `.deb` + AppImage per OQ-64 A), `tauri signer sign` on the artifacts with the updater signing key from repository secrets, assemble `latest.json` (platform → artifact + signature + notes), create the GitHub Release with all artifacts and upload `latest.json` to the same tag's assets (the released updater endpoint reads it per M3 — publishing to the same URL the app already reads closes the manual step; a draft-release pre-flight per NFR-11 tests the pipeline without consuming a version).
- **Repository secrets:** the updater minisign private key + its password (the signing key today lives only on the developer machine — moving it into a secret is part of this work; the public key stays in `tauri.conf.json` unchanged).
- **Failure semantics:** any job red = pipeline red. The wall gate (AC-58) is a *local* verification contract; per DR-353 the 300 s gate stays unchanged in this release (the raised budget remains a ledger item — the §5 cost model is the evidence for a later value), and the lane job reports its wall time as a job summary either way (D29's data source).
- **What CI does not replace:** the AGENTS verification phases are unchanged (Phase A stays feature-scoped local work; Phase B stays the user's real-app review; Phase C stays the post-Ship full regression). CI adds a *continuous* Phase-C-equivalent gate so the post-Ship run starts from a known-green baseline (the v0.0.9 Phase-C skip (DR-322) becomes unnecessary once every push is proven).

### 3.6 Repair items (D29–D32)
- **D30/D31 — the load-flake class** — the D28 recipe at the named points: `flowDelete`'s selection-clear step becomes a bounded wait-for-state with a re-query (the selection-cleared DOM condition), `flowImportProgress`'s search-typing step waits for a status-progress threshold instead of a fixed sleep; and, from the v0.0.10 Phase C run (ROADMAP §4), the same recipe at the newly named points — `flowOpenFolder`'s and `flowBulkFavorite`'s search-renders waits, `flowSortSecondary`'s settings→search sequence, the fixture-appearance waits in `flowReaderErrors`/`flowProtected`/`flowThemeAndSettings`, and self-sufficiency re-checks at the AC-47/AC-64/AC-09 checkpoints (each re-asserts its own precondition instead of trusting the previous flow's library state). All named flows are green standalone today; the AC is the full-shape behavior (the full lane run passes, the direct run passes).
- **D32** — `flowVirtualization`'s floor and restore wait become geometry-derived: measure the list viewport in the harness window, compute the expected window with the same rule `virtual.ts` exports (`indexAt` bounds plus `OVERSCAN` on each side, at the shipped `ROW_HEIGHT`), and assert the mounted count equals that derived window (plus the unchanged `< 60` ceiling). The literal 12 disappears from both the wait and the check; the NFR-01 claim it guards is unchanged.
- **D29 — per OQ-66 answer C (DR-348), budget half deferred by the user's value decision (DR-353: keep 300 s this release).** **(a)** The budget stays at 300 s; the raised value remains a ledger item (§5's measured cost model is the evidence base for the user's later call; CI's per-push wall-time data, NFR-10 AC-158, feeds it). **(b)** The shared read-only corpus is built: a 10 000-document corpus directory the scale lanes point their instances at instead of each importing its own (the import cost is the dominant term — M9).

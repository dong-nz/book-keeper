## Rendering (`src-tauri/src/pdf/mod.rs`)

- `RenderService` — a **single dedicated OS thread owns every pdfium call** (the DR-134 single-owner rule: the bundled pdfium's C API is not thread-safe, pdfium-render #262). One process-wide instance (`RenderService::shared()`), a request queue with a wake channel; every pdfium user in the app goes through it.
- `document_dto(render, path) -> PdfDocDto` — page count plus per-page geometry in points (the `app_pdf_document` payload). `render_page` honours the scale bounds and the 1-based page range; out-of-range requests are typed errors, not clamps.
- **The cover pipeline was rewired through the same service** (AC-63): `covers` no longer holds its own pdfium binding — a cover is the service's page-1 render. One pdfium owner for the whole app.
- Typed errors (FR-08/AC-69): an unopenable document reports `AppError::…` variants end to end — the reader helpers never panic and never open silently.
- **Page-encode tuning (v0.0.7, OQ-42 → DR-178/DR-196):** `serve_page`'s PNG stage writes with `PngEncoder::new_with_quality(…, CompressionType::Fast, FilterType::Sub)` (`pdf/mod.rs:450`) — lossless by construction (AC-74), measured 332 ms → 207 ms for a 1 932 px page render+encode, the cache key and file contract untouched (the encoder-identity test keeps its assertions). **Covers keep the balanced default encoder** — the tuning targets the reader's page-serving cost (the encode stage is ≈ 90 % of measured page CPU, M3); the cover pipeline is unchanged.
- **Bind-path fix (v0.0.12, D34, DR-400):** `bind_candidates(exe_path, cwd, extra_dirs)` searches: exe directory → `binaries/` beside the exe → **extra directories supplied at startup** (new: `lib.rs` starts the service with the managed resource directory's `binaries`; `EXTRA_BIND_DIRS` is a `OnceLock`, the first `start_service(extra_bind_dirs)` call wins) → `cwd/binaries` (dev). This closes the ledger defect: the published macOS `.app` places the library at `Contents/Resources/binaries/` and the `.deb` at `/usr/lib/Book Keeper/binaries/` (binary in `/usr/bin`) — both layouts missed the old search path, so the installed macOS app answered "Cannot read PDF" for every PDF and every cover job failed; Windows and AppImage had coincidentally hit the path (CI runs the source tree, DR-390). `bind_candidates_reach_the_packaged_macos_and_deb_layouts` builds both published layouts from the artifact shapes and proves the candidates reach the library.
- **Text extraction for the selection layer (v0.0.12, FR-30/UI-54, spec §3.3):** `RenderService::page_text(path, page, password)` runs pdfium's text SDK (FPDFText_*, the §0 dependency gate — the fetched binary exports the API) **on the same single service thread** and returns top-origin runs in page points (the y-flip from pdfium's bottom-origin baseline is proven against a fixture with known geometry); `MAX_TEXT_RUNS = 4_000` bounds the list and a page beyond the cap is served capped with `truncated` flagged; a page without text extracts nothing — not an error (that is the scanned-page case). `serve_text` (the `app_pdf_text` path) caches the extraction in the reader cache as `<reader_dir>/<doc-key>/text-<page>.json` (`reader_text_path`) and serves a cache hit as-is; `remove_document_cache` / `clear_reader_cache` clear text files through the identical code path as page images (AC-62/AC-67 discipline). The password state maps to the released typed errors unchanged.

## Commands (thin wrappers, R1.2)

- `app_pdf_document(id) -> PdfDocDto` and `app_pdf_page(id, page, width) -> rendered page data` (`commands.rs`): resolve the document path (`resolve_open_target` — a `missing` document yields the typed error first), then hand the request to the service.
- `app_open_reader_window(id)`: **create-or-focus.** Missing file → typed error before any window exists (the toast's Relink path). Otherwise ensure the window labeled `reader-<id>`; an existing window is focused instead of a second being built (FR-17's one-window-per-document rule, enforced at the command).
- `app_open_document` (the v0.0.1 OS path) is unchanged — it is now reached only from the context menu's *Open in external viewer* item (UI-31).
- **`app_pdf_outline(id) -> Vec<OutlineEntry>` (FR-18, v0.0.7)**: resolve the path, then `pdfmeta::outline` (lopdf `get_toc`, flattened to `{title, page (1-based), depth}`); an unopenable file yields the typed error, a file without an outline an empty list — the UI shows no ToC control for an empty list (AC-78).
- **`app_pdf_text(id, page) -> PageTextDto` (v0.0.12, FR-30, §3.3)**: `page ≥ 1` validated at the boundary, then `serve_text` (cache-or-extract, §Rendering above); the DTO is `{page_width_pt, runs: [{text, x, y, w, h}], truncated}` in page points, top-origin.
- **`app_reader_position_get(id)` / `app_reader_position_set(id, value)` (v0.0.12, FR-28, §3.2)**: thin wrappers over the new `src-tauri/src/positions/` module — the memory lives in the `settings` table under the key `reader.pos.<id>` (`key_for`), a compact JSON value with exactly one anchor: PDF `{"p":<1-based page>,"o":0..1}`, EPUB `{"c":<1-based chapter>,"o":0..1}`; `validate` rejects anything else at the boundary, an unknown document id is the typed error, `cleanup(ids)` removes a document's key. Positions are app state, not library data: they never ride the settings DTO or the `settings_changed` broadcast (`position_rows_do_not_bloat_the_settings_dto` proves the DTO is exactly `SETTINGS_KEYS`), `delete_documents` removes them in its transaction, relink/rename keep them (the id is unchanged). No new settings command: the pair is separate by design (per-document values would bloat every window's settings payload — AC-166 no-bloat half).
- **View-mode memory (v0.0.12, FR-29, §3.2)** rides the **released** settings path, not a new command: the settings key is `view_mode` (added to `SETTINGS_KEYS` and `SettingsDto`), validated against `single | continuous | facing | horizontal` with the released default `continuous` for an absent or invalid stored value — the exact typed-filter pattern `view`/`sort`/`dir` use; writes go through `settings_set` (the debounced batch), every window learns changes through `settings_changed`. *(Spec §3.2 named the key `reader.view_mode`; the released key is `view_mode` — same typed pattern, consistent with the other settings' bare key names. Recorded here as released; the correction is a documentation fact, the behavior is the agreed one.)*
- Every command above sits in the `ui/src/api.ts` whitelist (v0.0.12 adds `app_pdf_text`, `app_reader_position_get`, `app_reader_position_set`; the cover commands are listed in [covers.md](covers.md)); `tests::command_router_matches_the_ui_command_client` (AC-41) holds router and client in step.

## Windows (`src-tauri/src/lib.rs`, capabilities)

- `WebviewWindowBuilder` with label **`reader-<id>`** — the document id *is* the window key, mirroring the cache directory name. Default 1000 × 700 CSS px, OS cascade placement, resizable, minimizable, titled with the document's filename.
- **Frameless replication** (UI-30, OQ-40 → DR-140): the reader window carries the same frameless chrome as the library window (its own window-controls strip), not an OS title bar.
- `src-tauri/capabilities/reader-windows.json` grants the window-operation capabilities to `reader-*` windows only — the library window's capability set is untouched.
- `on_window_event(Destroyed)` for a reader window calls `pdf::remove_document_cache` (AC-67): the cache is session-scoped, keyed by the document id, written by `app_pdf_page` under `<data_dir>/reader/<id>/`; the asset-protocol scope entries serve exactly those directories.

## Reader UI (`ui/src/ReaderApp.svelte`, `components/ReaderView.svelte`, `components/ReaderControls.svelte`, `lib/state/reader.svelte.ts`)

- `ReaderApp.svelte` is the reader window's entry (a second window URL; `main.ts` mounts the reader app when the window label is `reader-*`). The surface shows no library chrome: no toolbar, no menus, no status bar (UI-30).
- **One state source** (DR-155): scroll position lives in the reader store; the `n / N` label and the mount window derive from the same observed position — the label is never relayed through parent state.
- **Request order** (DR-150): the current page is requested first; the mount window is requested only after the current page arrives. Page state is gated on the measured CSS width (DR-154): a zero-width startup layout cannot satisfy first-page readiness, and `pageAt` never reports a phantom last page.
- **Two-stage rendering** (DR-151, re-specified DR-153; presentation re-specified in v0.0.9 by DR-316/DR-318/DR-319/DR-323 — the Rust pipeline and the request widths are unchanged): the preview request is `min(display width in CSS px, 1400 px)` — a fast render that lands inside the NFR-08 budgets — then the full target arrives. The replacement is **presented, not swapped**: the full stage mounts as an overlay `<img>` above the preview and cross-fades in (DR-316 — the resolution seam the user saw as a "flash" is hidden by the fade). The mounted-page branch is **structurally invariant** (DR-318): the overlay element is always rendered, its `src` absent until the full stage arrives and filled by an attribute-only patch — the base image node is never torn down, so the already-painted preview never re-decodes. `#setImage` **discards any write whose captured width no longer equals the current `pageWidth(page)`** and the two-stage chain stops after the preview when a request has been superseded (DR-319 — a stage from a superseded request never enters the map; a discarded stage is always replaced by the in-flight current-width request, which the mount rule re-issues whenever `pageWidth` changes). When the cross-fade completes, `previewShown` publishes the full stage as the base `src` (an invisible attribute-only patch under the already-opaque overlay) and clears the overlay `src` — the steady state is **one decoded raster per mounted page**, as before v0.0.9 (DR-323: keeping both rasters alive for the mounted lifetime thrashed the WebView2 image cache and broke the AC-73/AC-96 budgets). The 75 % row stays single-stage fast.
- `overflow-anchor: none` on the reader scroller (DR-152): scroll position is exactly what the app sets; browser scroll-anchoring compensation (measured drifts of one page pitch / one viewport) cannot move it. The released list/grid scroller carries the same rule by the user's decision.
- Controls (UI-30 as amended by DR-206/DR-221, v0.0.7): the strip sits along the window's **bottom edge** (`ReaderControls` rendered last; the top chrome carries only the document's full name, ellipsis only on overflow — no strip at all in the error state, DR-238). Prev/next, a page field accepting a number, `PgUp`/`PgDn`/`Home`/`End`; **zoom is a select** — `fit-width` (default) / `fit-page` / `actual` plus the percent ladder `ZOOM_STEPS = [50,75,100,125,150,200,300]`, the percents anchored to the page's actual size (`actualSizeWidth(width_pt)` from the PDF geometry — 100 % *is* the actual size); `Ctrl`+`+`/`Ctrl`+`−` walk the ladder, `Ctrl+0`/`1`/`2` select the fit modes (DR-221). Zoom re-derives on window resize while keeping the viewed page.
- **View modes (UI-34, DR-180/DR-181/DR-204/DR-205/DR-215/DR-219/DR-224/DR-227, v0.0.7; MODIFIED in v0.0.10 by DR-290 — the fourth mode):** the store's `viewMode` — `single | continuous | facing | horizontal` — is the single layout source; the strip's view control (`MODE_BUTTONS`, four entries) switches it. **Memory changed in v0.0.12 (FR-29, OQ-68 answer A): the mode is remembered, not session-only** — `setViewMode` writes the `view_mode` setting (the released debounced settings batch) and every new reader window constructs its store from the remembered mode (`settings.readerViewMode` at store init); this supersedes DR-181's "every new window starts continuous", and the v0.0.7/v0.0.10 lane assertions that stated the old default were re-pinned to the new contract by DR-409. `single`: one page mounted (the current index), centered; at a scroll edge one wheel notch or one `↑`/`↓` press turns exactly one page (`edgeStep`, DR-227); the prefetch window queues movement-direction-first from the mounted index (DR-224). `continuous`: the released vertical column. `facing`: consecutive pairs (DR-180), pair-wise navigation; odd last page mounts alone. Pages are horizontally centered in all vertical modes (DR-205). **`horizontal` (UI-34 MODIFIED, SPEC-v0.0.10 §3.3):** the continuous model on the horizontal axis — pages in one left-to-right row at the current zoom with a fixed gap; the scroller scrolls sideways (wheel/drag), never the default mode. The store derives the viewed page from the row's horizontal scroll offset (`pageAt` over the row's width-based prefix offsets, computed from the same geometry the vertical modes use — no measured-image guessing); `stepPage` moves one page along the row, `scrollNotch` scrolls the row by one notch, a viewport step travels the viewport width along the row; fit-width fits the page named by the horizontal position; the mount window and the serving pipeline key on row proximity (at a document's end only row-near pages are mounted). Mode switches re-derive position in both directions keeping the viewed page (the AC-144 handoff chain). The serving pipeline, page cache and measured budgets are mode-independent and were not touched (the released closing clause held: no Rust change in this release).
- **Position memory (v0.0.12, FR-28, spec §3.2; application point per DR-406):** the store tracks the current position (anchor page/chapter + a normalized offset 0..1) and writes it through `app_reader_position_set` on a **debounced 1 s cadence** (`POSITION_WRITE_MS`, "no per-scroll/per-paint writes") plus a flush on window close (`onunload`/`Destroyed` path) — a position written just before close is present after re-open (AC-168). On open the remembered value is fetched (`app_reader_position_get`) and **applied before the first page paints**: while a restore is pending the mount effect requests nothing — page 1 is never fetched or painted; the PDF view applies it in its first-fit-measurement step (`applyRestoredPosition`, after the store has real geometry), the EPUB view after its first measure (DR-406 1; the first view-level run found two EPUB restore defects — the pending range covering the whole spine and landing against a not-yet-measured stack — both fixed by DR-407). A stale anchor (a relink to a shorter file) is clamped to the nearest valid position at decode (`decodeReaderPosition` clamps the anchor to the document's extent; exactly one anchor key accepted, offset 0..1, values rounded to three decimals on encode — sub-pixel fractions carry no reading meaning). No position UI anywhere: no prompt, no "continue reading" surface (FR-28's stated boundary). Storage side in §Commands above.
- **Text selection surface (v0.0.12, FR-30/UI-54, spec §3.3):** `components/TextLayer.svelte` mounts over a shown raster only when that page's runs exist — `runs.length > 0` (a scanned page gets no layer and no message). The layer is positioned spans computed by `textPositions()` — the `displayWidth / page_width_pt` ratio maps the top-origin page-point runs to CSS px, sitting on the raster pixel for pixel, **re-derived on zoom and mode change, never measured** (the same no-measurement rule as the page box; pure arithmetic on the store's exact geometry). The layer is transparent until used; selection color comes from the theme (`--selection-tint`, `::selection`). Runs are fetched lazily for pages entering the render window (`app_pdf_text` through the store, per-window cache). Copy is the native path: the reader key map intercepts no `Ctrl+C`/`Ctrl+Insert`, so the OS selection/copy behavior works over the layer. The EPUB reading column gets a scoped `user-select: text` override in `EpubReaderView.svelte` (the M5 scoped-override pattern; surface in [reading-epubs.md](reading-epubs.md)). Boundaries as agreed (spec §2): selection is not persisted, no highlights, no in-document search, no OCR — a text-less page stays a picture.
- **Reader cover menu (v0.0.12, UI-55):** `components/CoverMenu.svelte` joins the top chrome's right-end control cluster (left of the settings control; on macOS the whole cluster sits at the left end per UI-07 MODIFIED), ready-state only — full design in [covers.md](covers.md) §Manual cover selection.
- **ToC panel (UI-33 as revised by DR-218/DR-223/DR-226/DR-232/DR-236/DR-239…DR-244, v0.0.7; the pin added in v0.0.10 by FR-24/UI-49, revised by DR-335…DR-337/DR-342/DR-343):** the strip shows the ToC control only when `app_pdf_outline` returns a non-empty tree; the panel opens collapsed to depth 1; a fixed bar across the panel top carries the single expand-all/collapse-all toggle (icon-only, tooltip names the action); the tree scrolls independently below it; entry click jumps via the page field's own path; `Esc` closes the panel before the window (the reader key map's `overlayCount` guard). **Pin (UI-49):** the panel's toolbar row carries a pin toggle at its right end (`aria-pressed`, static accessibility per DR-331; its glyph follows the state — `unpin`/`pin` icons, DR-336). State lives on the host window's store as two booleans — `tocPinned` (layout mode) and `tocDockedOpen` (the docked panel's visibility; visibility and pin separated by DR-337; the name avoids the `tocOpen` collision with the released overlay-visibility getter) — **session-scoped** (OQ-60 → DR-327: never persisted; a new window starts unpinned). Pinned: the panel renders as a docked column at the window's left edge from below the chrome strip to the control strip at the token width (`TocDocked` hosts the shared `TocPanel`/`TocTree`/`TocEntryContent` components — one tree, no per-host branch, M9); the reader layout reserves the panel column (the page area's content box shrinks, fit-width follows the shrunken box, serving delivers at the shrunken fit width — the horizontal row occupies the shrunken column too); the docked toolbar row flexes from its own shared `.toc-toolbar` recipe, so the pin lands at its right content edge in both states (DR-342). Stacking (DR-343): the docked panel is layout — it paints above the page surface and below every floating overlay (menus, dialogs); `Modal.svelte`'s Escape rule answers only for kit menus (the `data-state` marker) so a closing menu can no longer swallow a dialog's `Esc` (DR-347). Entry selection keeps a pinned panel open; `Esc` closes it first and keeps the docked position; the ToC control hides/re-shows it at the same docked position; the panel's pin control is the only un-pin path; unpinning restores the released overlay.
- **Keyboard (UI-30 extended by UI-39, DR-228, v0.0.7; UI-39 MODIFIED in v0.0.10 for the horizontal mode):** `ReaderApp`'s key map adds `←`/`→` (= the strip buttons, `store.stepPage`) and `↑`/`↓` (= one `SCROLL_NOTCH = 100` wheel notch, `store.scrollNotch`); every navigation key is guarded while a text field, the ToC panel or a menu is open. In `horizontal` the same store paths carry the per-mode meaning (UI-39 MODIFIED): `←`/`→` step one page along the row, `↑`/`↓` scroll the row sideways by the notch — the faithful counterpart of the wheel — and `PgUp`/`PgDn` travel one viewport along the row; `Home`/`End`, the page field and the released guards are unchanged. The reader window's own `Esc` reaches the window after a just-closed menu: the guard decides from the app's overlay registry in capture phase (DR-340), and the released dialog answers only for kit menus (DR-347).
- **Reader settings menu (FR-24/UI-50, DR-331/DR-338/DR-344, v0.0.10):** the shared `SettingsMenu.svelte` component — the library window's own menu, item list never duplicated — renders in the reader window's top chrome, immediately before `WindowControls`, in **every** reader window (the PDF gate removed by DR-344; the EPUB window hosts it identically). Its items are the released ones: the theme cycle (writes through `settings.setTheme`, R1.6 — the released `settings_changed` re-apply path applies it live in every window) and *Settings* (opens the released settings dialog in the reader window itself); the *Check for updates* item works there because `updater:default` joins `capabilities/reader-windows.json` (DR-344) — the whole update surface is in [keeping-the-app-updated.md](keeping-the-app-updated.md). No new i18n keys (the main menu's keys are reused; the earlier reader-only label key was removed, no dead code).
- Theme application (v0.0.7, DR-230): the settings service emits `settings_changed` on save; every window — reader windows included — re-resolves the ramp live (see [settings-and-appearance.md](settings-and-appearance.md)).
- Error surface (AC-69): an unrenderable file shows a reader error state with an **Open in external viewer** action that performs `app_open_document` exactly once.

## Invariants

- One reader window per document: the window label, the cache directory and the create-or-focus rule all key on the document id.
- Every pdfium call in the app runs on the `RenderService` thread — covers and reader included.
- The reader window shows no library surface and holds no library state; closing it changes nothing in the library.
- First-page readiness and page state derive from measured layout (CSS width), never from a pre-layout estimate.
- Reader position memory is settings-table state keyed by document id (`reader.pos.<id>`): it never rides the settings DTO or its broadcast, is removed with document deletion (same transaction) and survives relink and rename (the id is unchanged). A restore is applied before any page is fetched — opening a remembered document never fetches page 1 first (v0.0.12, FR-28).
- The text layer is derived data: the same page-point geometry the page box is sized at, mapped by arithmetic, never measured, never part of serving or the raster (v0.0.12, FR-30).

## Detection (`src-tauri/src/library/service.rs::rescan`)

- Runs at startup and on the manual **Rescan** command only (DR-13) — no background timer, no watcher.
- For every row: file gone → `UPDATE documents SET missing = 1`; file present → flag cleared, `size`/`mtime` refreshed, cover job re-enqueued when the file identity changed (covers.md).
- Result reported as `RescanOutcome { missing_found, found_again }` → toast "N missing file(s) found" / "N file(s) found again".
- Opening a missing document fails with a typed `AppError` → error toast carrying the **Relink…** action (R4.6).

## Relink (`relink_document`)

- UI: `RelinkDialog.svelte`, a global singleton keyed by `feedback.relinkTargetId` — opened from the error toast action, the row's relink action, or the editor's **Relink…** button (which closes the editor first, since its snapshot would go stale). New path chosen via `tauri-plugin-dialog` native file picker; **since v0.0.9 (AC-128) the picker's filter is derived from the document's own extension** — relinking a book offers `epub` files, relinking a PDF offers `pdf` files (`documentFilters(filename)` in the dialog).
- Command: `library_relink(id, new_path)` — **since v0.0.9 the relink is type-matched (FR-22/AC-128):** the chosen path must pass `is_document_path` and `same_document_extension` against the stored path — a wrong-kind file is the typed `AppError::UnsupportedType` ("The file you chose is not a readable PDF or EPUB.") and the document is untouched. Then it verifies the file exists, updates `path`/`size`/`mtime`, clears `missing`, re-enqueues the cover. Before v0.0.9 the check was "parses as PDF" — single-type by construction.
- Title re-derivation is gated by `documents.title_source` (metadata-editing.md): `auto` → new title from the new filename; `user` → manual title survives the relink.

## UI state

- `data-missing` attribute on row/card drives the visual flag. The missing count moved with the rest of the status surface (status-feedback.md): the status bar exists only when there is something to report, so the count is carried by the Browse menu's *Missing documents* item (with its **Rescan documents** action; renamed in v0.0.7 per DR-211). Until v0.0.6 the Settings dialog's Library section also showed it; that section was removed in v0.0.7 (settings-and-appearance.md §3.14) — the Browse menu is now the only count surface.
- **Row action line (v0.0.4, D8):** `ROW_ACTION_IDS` is `favorite, details, delete, relink` — relink carries `applies: doc.missing` and the shared rendering order of `documentActions`, so a missing document's row/card shows **Relink** in the same sequence its context menu shows, and running it opens the same singleton dialog. Present files' rows are unchanged.
- **Missing-state rendering (v0.0.4, UI-25):** one state, one treatment. The row flag (`MissingBadge.svelte`) is plain `--warning`-colored text — no filled pill — with the last-known path as its tooltip (`data-path` hook); the card carries a compact tinted badge (warning-tinted ground, radius = half its height). The status surfaces (Browse submenu, Settings Library row, status bar) already reported plain warning text; the row now matches them. The colors are the D11 text-role values (settings-and-appearance.md).

- **v0.0.7 (DR-211, labels only):** the Browse submenu item is *Missing documents* and the rescan item *Rescan documents*; the status-bar warning reads "N documents missing"; the relink dialog title, the relinked toast and the rescan outcome toasts follow the same documents/file wording audit ("document relinked", "N missing document(s) found", "N document(s) found again") — catalog values only, keys and behavior unchanged. The last-known-location label over the row flag and card badge now renders in the app's own tooltip (the `data-path` hook wrapped in the shared `Tooltip` component instead of a native `title`; UI-37, the-app-window.md) — the text it carries is unchanged, its surface is the ramp's `--surface-1` with the overlay shadow.

- 2026-11-10 (v0.0.8 — FR-21 interaction; UI-40 gating) — **Detection and the relink flow are unchanged** (`rescan_missing`, `relink_document`, the `title_source` gating, the singleton relink dialog, the row/menu `applies: doc.missing` relink action). The new file actions are deliberately gated off for missing documents — `rename` and `open_folder` carry `applies: !doc.missing` — because both act on the file at the recorded path; a relinked document gains them like any other. A rename through the app moves `documents.path` itself ([renaming-a-documents-file.md](renaming-a-documents-file.md)), so the file stays present by definition and the missing-detection logic needs no change — it resolves by the new path (`flowRename` re-verifies relink and detection against the renamed file; AC-107).
- 2026-11-12 (v0.0.9 — FR-22/AC-128) — **Relink is type-matched.** `relink_document` validates the chosen path through `is_document_path` and `same_document_extension` against the stored path: a book relinks to a book file, a PDF to a PDF file; the wrong kind is the typed `UnsupportedType` (the dialog shows "The file you chose is not a readable PDF or EPUB.") and the document is untouched. `RelinkDialog` derives the picker filter from the document's own extension, so the wrong kind is normally not offerable in the first place. Detection (`rescan`), the missing flag and its surfaces, the row/menu action gating, the singleton dialog and the `title_source` gating are unchanged — a book row is a missing row like any other. Verified: `relink_is_type_matched` (Rust), `flowMissingAndRelink` EPUB section + derived-filter checks.

## CI pipeline — `.github/workflows/ci.yml`

**Triggers:** `push` and `pull_request`, both filtered to `branches: ["master"]` — tag pushes belong to `release.yml`; an unfiltered trigger would run CI on a pre-flight tag (DR-382). Concurrency group per ref with `cancel-in-progress`.

**`verify` job — three-OS matrix** (`windows-latest`, `macos-latest`, `ubuntu-24.04`), `fail-fast: false`: every layer reports its own verdict (AC-157). Step order is RULES workflow 3's order. **The UI lane runner is not a CI step (DR-390, the user's decision):** the real-app layer stays the local Phase-A/C entry point (`scripts/ui-verify.mjs`, unchanged); the Windows-only lane job, its `tauri-driver` install and its report-upload step were removed from the workflow before the first green run.

1. `actions/checkout@v7`; wall-clock start (AC-158).
2. Linux: Tauri system packages — build dependencies for the Rust layer only. **Since v0.0.12 (NFR-12 a, §3.4a)** the package list lives in `.github/linux-deps.txt` (shared verbatim with `release.yml`; the extraction `grep -vE '^[[:space:]]*(#|$)' … | tr '\n' ' '` reproduces the released inline list exactly), and an `actions/cache@v4` step keyed `apt-<os>-hash(linux-deps.txt)` with restore prefix `apt-<os>-` caches `/var/cache/apt/archives` plus the lists directory — a warm install is the measured ≈ 28 s shape instead of the cold one.
3. `pnpm/action-setup@v6` (pnpm 12.4.1) + `actions/setup-node@v7` (Node 22, pnpm cache against `ui/pnpm-lock.yaml`); `dtolnay/rust-toolchain@stable` + clippy; `Swatinem/rust-cache@v2` with `key: app-<os>` — **since v0.0.12 (NFR-12 b) one shared suffix across `ci.yml` and `release.yml`** (the released `ci-<os>`/`release-<os>` pair was replaced): a recent `master` push's cache entry is what a tag build restores.
4. `node scripts/fetch-pdfium.mjs` — the sidecar is fetched, never committed (DR-50c).
5. `pnpm install --frozen-lockfile`.
6. **The layers, in order:** `cargo test` → `cargo clippy -- -D warnings` → `pnpm test` (vitest) → `pnpm run check` (svelte-check). Any red layer fails the pipeline.
7. Job wall-clock summary (every job, `if: always()`).

**`summary` job** (`needs: verify`, `if: always()`): reads the run's own job records through `gh api …/jobs` piped through `scripts/ci-summary.py` — per-job wall times plus the run's combined span, published to the step summary regardless of verdict (AC-158, D29's data source).

## Release pipeline — `.github/workflows/release.yml`

**Trigger:** `push` tags `v*`. **Version guard** (first step): the tag's version — everything before the first `-` — must equal `tauri.conf.json`'s version; a `-`-carrying tag is a pre-flight (allowed against the matching base version, e.g. `v0.0.10-preflight` proves the pipeline of a 0.0.10 tree without consuming a version).

**`build` job — matrix `include`** (one entry per OS, `fail-fast: false`): per-entry `fetch-pdfium` flags (`--universal` on macOS per DR-359 — the sidecar must match the universal bundle), `extra-rust-targets` (`x86_64-apple-darwin` on macOS), and `bundle-dir` — **macOS uploads from `src-tauri/target/universal-apple-darwin/release/bundle/`**: a `--target` build writes under the target name (DR-385). Pdfium fetch passes `secrets.GITHUB_TOKEN` (DR-384: the runners' shared unauthenticated IPs hit GitHub's 60/h limit). **Since v0.0.12 (NFR-12) the Linux job's cache steps are the shared ones:** the same apt-cache step as `ci.yml` (same `.github/linux-deps.txt`, same key) and the same `key: app-<os>` rust-cache suffix — a recent `master` push is what warms a tag build (AC-173's observation belongs to the first runs after the push).

**Build invocation** (the CLI from the repo root, like the harness): `tauri build --config '{"bundle":{"createUpdaterArtifacts":true,"targets":["nsis","msi","app","dmg","appimage","deb"]}}'` plus `--target universal-apple-darwin` on macOS. The config override is per-build only — `tauri.conf.json` stays as released (DR-358 b). The target union **includes `app`**: the macOS updater artifact (`Book.Keeper.app.tar.gz` + `.sig`) exists only because the app target is built (DR-385 — the shipped installers-only list has no darwin updater artifact). Signing: `TAURI_SIGNING_PRIVATE_KEY` from repository secrets (the keypair of DR-377, pubkey pinned in `tauri.conf.json`, id `E90D6DD0F1A54E35`); no password variable needed (verified with the CLI, DR-377).

**`publish` job:** downloads the three bundle artifacts into one directory, then:

1. **Flatten** (DR-387): `find` filtered to the artifact extensions (`exe msi dmg AppImage deb app.tar.gz sig`) into `tmp/release/flat/`, names normalized **spaces → dots** — GitHub's asset API rewrites spaces itself, so the flat names, the served asset names and the manifest URLs must agree on the dot form. The raw bundle tree (AppImage staging, deb intermediates — 269 files for 11 real artifacts in the fifth run) is never published.
2. **Manifest**: `node scripts/publish-release.mjs --dist tmp/release/flat --version <tag version, suffix stripped> --tag <tag> --repo <repository> --notes docs/release/notes/v<version>.md --out tmp/release/latest.json` — see below.
3. **Publish**: `softprops/action-gh-release@v3` with `files` = `latest.json` **first**, then `tmp/release/flat/*` (manifest first so a burst limit can never strand it); `draft: true` when the tag contains a `-` — a pre-flight release is invisible to `releases/latest`, which serves published releases only. That is what makes a pipeline pre-flight safe. **Since v0.0.14 (NFR-11 MODIFIED, design §3.8)** a `Prepare the release body` step before the publish writes `tmp/release/RELEASE_BODY.md`: the tag's base version's notes page (`docs/release/notes/v<version>.md`) copied **verbatim** when it exists — the release page shows the Markdown as written — otherwise a two-line pre-release text naming the tag and that it carries pre-flight artifacts; the publish step passes it as `body_path` (the action's released input). The manifest is untouched — its plain-text `notes` variant (OQ-74, v0.0.13) remains the app-side channel.

## The manifest — `scripts/publish-release.mjs`

- **Platform map** (the updater plugin's exact `{os}-{arch}` lookup, no universal fallback — DR-358 a): `windows-x86_64` → the NSIS setup exe (`*_x64-setup.exe`); `darwin-aarch64` **and** `darwin-x86_64` → the one universal artifact (`Book.Keeper.app.tar.gz` — no version, no arch in its name); `linux-x86_64` → the AppImage. The `.msi`, `.deb` and `.dmg` ship as installers; they are not updater entries.
- **Signatures:** each entry's `signature` field is the matching `.sig` file's text verbatim; a needed artifact with no `.sig` sibling → exit 1.
- **Version guard per entry:** versioned names must carry the manifest version (the darwin artifact carries none — checked by shape).
- **`notes`:** the first section body of the release notes page (`docs/release/notes/v<version>.md`), **published as plain text since v0.0.13** (OQ-74 closed A): `plainText()` converts the page's Markdown deterministically before the manifest is written — heading hashes removed, `*` bullets unified to `-`, emphasis and code markers stripped, links become `text (url)`, runs of blank lines collapsed; line and list structure stay — they are the notes' own layout. The text is what the released app shows in the update modal (UI-56); the page itself keeps its Markdown.
- **URLs:** the tag-form download path (`releases/download/v<version>/<dot-name>`) — valid once the release is published.

## Product identity (FR-27, the rename)

`productName: "Book Keeper"`, identifier **`com.bookkeeper`** — **changed in v0.0.12 by the D33 fix (FR-27 MODIFIED, the user's chosen value, spec §3.5)**: the released `com.bookkeeper.app` made the derived data directory look like an application bundle on macOS (the identifier is `app_data_dir`'s last path segment; Finder hides the `.app` suffix and opening the folder runs LaunchServices, which reports "it may be damaged or incomplete" — upstream tauri-apps/plugins-workspace#2461). Data directory platform-resolved under the new identifier — **no migration from `com.bookkeeper.app` or the old `com.pdfkeeper.app` path** (the user's decision, precedent DR-381; the old directory is left in place, its cleanup is the user's — stated in the release notes). The toolchain accepts the two-segment value exactly as built (`tauri-build` 2.7.4 splits on `.` only for the Android package name; no validator rejects it; GTK app-ID rules not in play — spec M13). The literal was pinned at five places (spec M11): `tauri.conf.json`, the two `ui-smoke.mjs` constants, `ui-verify.mjs`'s parallel-corpus path, and this document — all moved 2026-11-19; no Rust source literal exists. The binary is `bookkeeper.exe` with `binaries/pdfium.dll` beside it; artifact names carry the product name (`Book.Keeper_0.0.12_x64-setup.exe`, `Book.Keeper.app.tar.gz`, … — served in the dot form). The updater endpoint is `https://github.com/dong-nz/book-keeper/releases/latest/download/latest.json` (repository renamed same-day, DR-375).

## Verified artifact shape (the sixth pre-flight run, DR-388)

12 assets: `latest.json` + `Book.Keeper_0.0.10_x64-setup.exe`+`.sig`, `…_x64_en-US.msi`+`.sig`, `Book.Keeper_0.0.10_universal.dmg`, `Book.Keeper.app.tar.gz`+`.sig`, `Book.Keeper_0.0.10_amd64.AppImage`+`.sig`, `Book.Keeper_0.0.10_amd64.deb`+`.sig`; manifest with four platform entries whose URLs match the served asset names verbatim. Full pipeline ~24.5 min.

**What this pipeline's layouts exposed (v0.0.12, D34):** the macOS bundle places the bundled library at `Contents/Resources/binaries/` and the deb at `usr/lib/Book Keeper/binaries/` — neither is reached by the 0.0.11 app's bind search path, which is why the packaged macOS app could not read PDFs while the source-tree runs (where resources land next to the binary) never saw the defect. The fix (`bind_candidates` + the synthetic packaged-layout units) is designed in [reading-pdfs.md](reading-pdfs.md); no packaging change was needed — the layouts are correct, the search path was not.

## Test mapping (observation-type ACs — the pipeline runs are the tests)

- **AC-157:** a green CI run on a real push **and** a deliberately failing one (the red exercise: a throwaway failing Rust test on `master`, proving a red test layer turns the matrix red with `fail-fast: false`); run records cited in the Build ledger.
- **AC-158:** the `summary` job's per-job + combined wall report on those runs.
- **AC-159:** the release page's artifact list — met by the pre-flight (run 44250608428) and reproduced by every real tag.
- **AC-160:** the published manifest resolved by a running app — the manifest half via the published release; the app half is the user's installed-app observation (the fixture path `flowAppUpdate` remains the in-app behavior proof, unchanged since v0.0.10).
- **AC-173 (v0.0.12, NFR-12):** a CI run shows the apt step warm (recorded step time, cache hit) and a release run following a recent `master` push shows the shared Rust cache in use with its ubuntu job at or below ≈ 400 s — observed in pipeline output, numbers recorded not asserted; the observation belongs to the first runs after the v0.0.12 push and is recorded in ROADMAP §4 when it lands.
- **AC-202 (v0.0.14, NFR-11 MODIFIED):** the published GitHub Release body carries that version's notes page (Markdown as written); the pre-flight shape carries the pre-release line — observed on the release page the Ship tag publishes (the AC-160 pattern: the pipeline run is the test), recorded in ROADMAP §4 when it lands.
- **Local guards proven during build:** YAML validation of both workflow files; the version guard's four tag cases; the assembler dry-run against the *real* run-4/run-5 artifacts (4 entries, real signatures) with the negative case red; the tar invocation under GNU tar 1.35; `fetch-pdfium.mjs --universal`'s darwin-only guard.

## Invariants

- CI runs the same commands as the local Phase-C, minus the real-app layer, which stays local (DR-390) — CI defines no second verification language (RULES R6).
- A pre-flight never consumes a version and never reaches users (draft + invisible to `releases/latest`).
- The Release carries only the filtered artifacts; the manifest is always uploaded first.
- `tauri.conf.json` stays as released; every packaging behavior lives in the workflow's per-build override.

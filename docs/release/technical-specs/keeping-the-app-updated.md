## What this feature is

Self-update on the GitHub Releases channel: a silent startup check, a manual *Check for updates* in the Settings menu, and an in-app install through the platform installer. The whole discovery-and-install engine is the official `tauri-plugin-updater` (2.14.1, the user's option-A answer, DR-321): fetch of `latest.json`, version comparison against the compiled app version, minisign signature verification, artifact download with progress events, installer launch, app exit. Since v0.0.13 the completion path on macOS/Linux is covered too: `tauri-plugin-process` (2.4.0, approved by the user's OQ-75 answer, DR-422) supplies `relaunch()` — after an install completes on those platforms the app surfaces the completion and restarts itself (the plugin's Windows path already exits the app and the installer restarts it, spec fact F2). The app contributes only the surfacing — since v0.0.13 a found update surfaces as the update modal (UI-56), completion/up-to-date/failure as toasts, progress as the job bar, and nothing else (UI-52 as MODIFIED).

## Backend (`src-tauri/`)

- **Registration only** (`lib.rs`, the plugin builder chain): `.plugin(tauri_plugin_updater::Builder::new().build())` and, since v0.0.13 (DR-423), `.plugin(tauri_plugin_process::init())`. No hand-written `app_*` commands — the plugins' own commands (`plugin:updater|check`, `…|download_and_install`, `…|download`, `…|install`, and from v0.0.13 `plugin:process|restart`) are the entire command surface, the pattern the opener plugin established (UI-40). Because there are no custom commands, R1.2 has nothing to wrap and the command-router↔client set-equality test is untouched; the frontend reaches the plugin through its typed JS client, not through `ui/src/api.ts`.
- **Config** (`tauri.conf.json` → `plugins.updater`): `endpoints = ["https://github.com/dong-nz/book-keeper/releases/latest/download/latest.json"]` (renamed from `dong-nz/pdf-keeper` 2026-11-18, v0.0.11 DR-375), `pubkey` = the minisign public key of the release signing keypair (base64 untrusted comment, key id `E90D6DD0F1A54E35`). The plugin accepts only `https://` endpoints unless `dangerousInsecureTransportProtocol` is set — the shipped config does not set it; only the test-harness override does (below).
- **Manifest entry** (DR-330): `serde_json = "1.0.154"` is declared in `Cargo.toml` because `tauri::generate_context!` expands to code calling `serde_json::from_str` by name once a `plugins` section exists. Zero new crates enter the graph — the same artifact tauri already builds, named in our manifest.
- **Settings key (v0.0.13, FR-25 §3.2, AC-193):** the Skip persists through the released settings commands — no new command. `library::SettingsDto` carries `update_skipped_version` (`""` = nothing skipped), `SETTINGS_KEYS` lists `update_skipped_version` (11 keys), and `library::service` validates on read: `is_valid_skipped_version` accepts `""` or a canonical three-segment `x.y.z` — the same pattern as the other value validators — a corrupt row falls back to "nothing skipped". The comparison itself is frontend string equality (spec fact F13); the backend guarantees only the shape of the stored value. A change reaches every window through the released `settings_changed` path (DR-230).
- **Capabilities:** `updater:default` in `capabilities/default.json` (main window) and — since DR-344 — in `capabilities/reader-windows.json` too: UI-50 as revised (DR-338/DR-344) puts the complete Settings menu, including *Check for updates*, in every reader window's chrome, and the plugin's commands are capability-gated per webview, so the grant must follow the menu. From v0.0.13 (DR-423) both files also carry `process:allow-restart` — the only `tauri-plugin-process` permission the app uses; the updater capability's per-window logic applies unchanged to the completion relaunch, which the update flow can reach from any window that has the Settings menu.

### Release signing (maintainer's handling)

The keypair was generated with `tauri signer generate` (empty password). The **private key lives outside the repository** at `%USERPROFILE%\.pdfkeeper\signing\key_pair.crt`. Publishing a release that the app can install means: build the platform artifact, sign it with `tauri signer sign <artifact> --app-version <version>` (private key + password), and publish `latest.json` in the *dynamic* manifest form — `{version, notes, pub_date, url, signature}` — where `signature` is exactly the `tauri signer sign` output and `url` points at the signed artifact. A manifest signed with any other key fails verification and surfaces as the check's typed error. Rotating the keypair means replacing `plugins.updater.pubkey` in the same release that ships the new key.

## Frontend (`ui/src/`)

- **`lib/updates.ts`** — the whole app-side surface (122 lines as shipped by v0.0.13, no business logic: the R1.2 shape holds on this side too). `checkForUpdates(manual)`: one shared path for the startup call and the menu item, guarded by a `checking` flag so they cannot interleave. `check()` resolving an `Update` arms the update modal through `armOffer` (UI-56); resolving `null` (current version) reports `updates.uptodate` **only for a manual check**; a rejected check reports `updates.checkFailed` as the typed error toast **only for a manual check** — the plugin's own transport text is never shown (AC-151). Arming rules (DR-332 item 2, as MODIFIED by SPEC-v0.0.13 §3.2): a startup arm whose version equals `settings.updateSkippedVersion` closes the `Update` resource and asks nothing (AC-184/AC-186 — plain equality is enough, the plugin only ever reports strictly newer versions, spec fact F13); a manual arm always re-presents (AC-187); the same version already on screen is not re-armed; a superseded or re-presented `Update` resource is `close()`d — the client's own contract, as is one whose install failed. Install: `downloadAndInstall` with the event callback feeding the released job-progress affordance as job kind `update` (`job.update` = "Downloading…") from `Started`/`Progress`; when `Started` carries no `contentLength` no bar appears (the affordance stays determinate, DR-332 item 4); the modal closes on the click — the bar is the surface while the install runs (§3.3). Completion handling changed with v0.0.13: on macOS/Linux `downloadAndInstall` resolves and the completion path runs — bar cleared, offer cleared, resource closed, `feedback.notify("updates.installed")`, a 1 500 ms visible beat, then `relaunch()` from `tauri-plugin-process` (OQ-75's answer A, AC-189); the Windows path never reaches that code — the plugin launches the platform installer and ends with `std::process::exit(0)` inside the call (spec fact F2; AC-152's Windows behavior unchanged). On failure the bar is closed and `updates.installFailed` is reported. `skipOfferedUpdate()` is the modal's *Skip this version*: persist through `settings.skipUpdateVersion` (written immediately — the skip must survive a restart made right after it, AC-186) and close the offer.
- **Offer store** (`state/updateOffer.svelte.ts`, ADDED by v0.0.13, UI-56): window-local `$state` — `offer: { newVersion, notes } | null` with `arm`/`clear`. Per-window like every other window state: a check in one window arms only that window. Closing the dialog without choosing is the session deferral — nothing is persisted; only the modal's *Skip this version* writes, through the settings store.
- **Update modal** (`components/UpdateModal.svelte`, ADDED by v0.0.13, UI-56): the released `Modal` component (the delete/rename dialog family), width 480, rendered from the offer store, mounted in both window roots (`App.svelte`, `ReaderApp.svelte` — the same placement the other dialogs have). It names the version the app is running (from the `appinfo` store — [status-feedback.md](status-feedback.md)) and the offered version, shows the manifest's `notes` as plain text whose line structure the modal preserves (`white-space: pre-line`, one `<p>` — OQ-74 closed A: the pipeline publishes plain-text notes; no markdown rendering), and carries the actions **Install** and **Skip this version**. No new dialog machinery.
- **Settings skip key** (`state/settings.svelte.ts`, v0.0.13): `updateSkippedVersion` state + `skipUpdateVersion(value)` writing the settings key `update_skipped_version` immediately; a stored value is read only through `parseSkippedVersion` — a value that is not a version reads as empty, so a malformed row can never silence a real update (the backend validates the same shape at the source, above). No schema change: the settings table is key-value, and v0.0.13 touched no schema at all.
- **Startup call** (`App.svelte`, end of the mount sequence): `void checkForUpdates(false)`. `App` mounts only in the main window (`main.ts` routes reader windows elsewhere), so "never on reader windows" is structural, not a condition (DR-332 item 5). The call is fire-and-forget: nothing awaits it, so no window activation waits on the network (AC-153).
- **Menu item** (`components/SettingsMenu.svelte`): *Check for updates* sits between *Settings…* and *About…*, reusing the released `rescan` glyph (circular arrows — the platform's check-for-updates mark, DR-332 item 3); the shared component means the item exists in the library window and in every reader window alike (UI-50 as revised).
- **Feedback store** (`state/feedback.svelte.ts`): the v0.0.11 shape minus what v0.0.13 made obsolete — `notifyWithAction`, the accessor of the retired availability toast, was deleted with it (R7, no dead code). The DR-332 item 1 auto-dismiss rule stands as shipped behavior: an info toast auto-dismisses only when it carries no action; the action clause now serves error toasts only (`reportError`'s optional action — the relink/delete affordances). `notify()` is unchanged.
- **i18n** (`i18n/en.ts`): `updates.modal.title` ("Update available"), `updates.install`, `updates.skip` ("Skip this version"), `updates.installed` ("Update installed — restarting"), `updates.uptodate`, `updates.checkFailed`, `updates.installFailed`, `job.update` — all through the coverage test. The availability-toast keys `updates.available`/`updates.availableNotes` were deleted with the toast (v0.0.13); the modal shows the manifest's `notes` text as-is, so no notes wrapper key exists.

## Invariants

- The app never compares versions, parses manifests, verifies signatures or launches installers itself; the only decision in `updates.ts` is the skip comparison — a plain string equality against a version the plugin already decided is newer (spec fact F13), not a version decision.
- The startup path is silent by construction: startup failures and a current app produce no toast, no bar, no state; only a found update arms the offer (AC-153 / UI-52).
- No window activation depends on the update check; nothing in the mount sequence awaits it.
- The availability affordance is the update modal (UI-56), never a toast — UI-52 as MODIFIED by v0.0.13. At most one offer is armed per window at a time (the armed version is tracked; superseded resources are closed). A startup offer is silenced only by exact equality with the skipped version; a manual check always re-presents (AC-184/AC-187).
- An install always ends with the app running the new version; there is no in-place swap of running code. On Windows the plugin's installer launch ends the app (spec fact F2); on macOS/Linux the app completes the install, surfaces the completion and relaunches itself (v0.0.13, OQ-75's answer A). Both paths reach the same state.

## What this feature does not have (stated so nobody builds it by accident)

Automatic download or automatic install — installing is always the user's click; *Skip this version* is a mute, not an install. Release-notes browsing beyond the manifest's `notes` text (the modal shows that text as plain lines; the pipeline publishes plain-text notes, OQ-74's answer A). Update channels, beta tracks, or a configurable source. A background re-check while the app runs (the check runs at startup and when asked). Any update UI of its own in a reader window beyond the shared Settings menu (the menu is chrome, UI-50; the update flow surfaces through that window's own modal and toasts). Delta/differential updates (the full artifact downloads). A persisted "never show updates again" (the skip is per version; *Check for updates* always re-presents). On Linux the in-app update is the AppImage run's path; a `.deb` installation updates by installing the new package (OQ-76's answer A).

# Keeping the App Updated — technical reference

**Since v0.0.10** · Requirements: FR-25, UI-52 (ADDED) · v0.0.10 decisions DR-321 (the reserved scope joins the release), DR-329 (the plugin wiring), DR-330 (the `serde_json` manifest entry), DR-331 item 5 (the fixture port), DR-332 (the surfacing rules), DR-344 (the updater capability in reader windows) · User guide: [features/keeping-the-app-updated.md](../features/keeping-the-app-updated.md) · Spec: [SPEC-v0.0.10.md](../../specs/SPEC-v0.0.10.md) §2 (FR-25, UI-52), §3.11 (technical design), §4 (AC-151–AC-153)

## What this feature is

Self-update on the GitHub Releases channel: a silent startup check, a manual *Check for updates* in the Settings menu, and an in-app install through the platform installer. The whole discovery-and-install engine is the official `tauri-plugin-updater` (2.14.1, the user's option-A answer, DR-321): fetch of `latest.json`, version comparison against the compiled app version, minisign signature verification, artifact download with progress events, installer launch, app exit. The app contributes only the surfacing — through released affordances and nothing else (UI-52).

## Backend (`src-tauri/`)

- **Registration only** (`lib.rs`, the plugin builder chain): `.plugin(tauri_plugin_updater::Builder::new().build())`. No hand-written `app_*` commands — the plugin's own commands (`plugin:updater|check`, `…|download_and_install`, `…|download`, `…|install`) are the entire command surface, the pattern the opener plugin established (UI-40). Because there are no custom commands, R1.2 has nothing to wrap and the command-router↔client set-equality test is untouched; the frontend reaches the plugin through its typed JS client, not through `ui/src/api.ts`.
- **Config** (`tauri.conf.json` → `plugins.updater`): `endpoints = ["https://github.com/dong-nz/book-keeper/releases/latest/download/latest.json"]` (renamed from `dong-nz/pdf-keeper` 2026-11-18, v0.0.11 DR-375), `pubkey` = the minisign public key of the release signing keypair (base64 untrusted comment, key id `E90D6DD0F1A54E35`). The plugin accepts only `https://` endpoints unless `dangerousInsecureTransportProtocol` is set — the shipped config does not set it; only the test-harness override does (below).
- **Manifest entry** (DR-330): `serde_json = "1.0.154"` is declared in `Cargo.toml` because `tauri::generate_context!` expands to code calling `serde_json::from_str` by name once a `plugins` section exists. Zero new crates enter the graph — the same artifact tauri already builds, named in our manifest.
- **Capabilities:** `updater:default` in `capabilities/default.json` (main window) and — since DR-344 — in `capabilities/reader-windows.json` too: UI-50 as revised (DR-338/DR-344) puts the complete Settings menu, including *Check for updates*, in every reader window's chrome, and the plugin's commands are capability-gated per webview, so the grant must follow the menu.

### Release signing (maintainer's handling)

The keypair was generated with `tauri signer generate` (empty password). The **private key lives outside the repository** at `%USERPROFILE%\.pdfkeeper\signing\key_pair.crt`. Publishing a release that the app can install means: build the platform artifact, sign it with `tauri signer sign <artifact> --app-version <version>` (private key + password), and publish `latest.json` in the *dynamic* manifest form — `{version, notes, pub_date, url, signature}` — where `signature` is exactly the `tauri signer sign` output and `url` points at the signed artifact. A manifest signed with any other key fails verification and surfaces as the check's typed error. Rotating the keypair means replacing `plugins.updater.pubkey` in the same release that ships the new key.

## Frontend (`ui/src/`)

- **`lib/updates.ts`** — the whole app-side surface (~80 lines, no business logic: the R1.2 shape holds on this side too). `checkForUpdates(manual)`: one shared path for the startup call and the menu item, guarded by a `checking` flag so they cannot interleave. `check()` resolving an `Update` arms the availability affordance; resolving `null` (current version) reports `updates.uptodate` **only for a manual check**; a rejected check reports `updates.checkFailed` as the typed error toast **only for a manual check** — the plugin's own transport text is never shown (AC-151). Arming rule (DR-332 item 2): the same version already on screen is not re-pushed (tracked by the returned toast id); after dismissal or when a newer version arrives it re-arms, and a replaced `Update` resource is `close()`d — the client's own contract, as is one whose install failed. Install: `downloadAndInstall` with the event callback feeding the released job-progress affordance as job kind `update` (`job.update` = "Downloading…") from `Started`/`Progress`; when `Started` carries no `contentLength` no bar appears (the affordance stays determinate, DR-332 item 4). On success there is deliberately no completion handling: the plugin launches the platform installer and ends with `std::process::exit(0)` — the app exits (AC-152). On failure the bar is closed and `updates.installFailed` is reported.
- **Startup call** (`App.svelte`, end of the mount sequence): `void checkForUpdates(false)`. `App` mounts only in the main window (`main.ts` routes reader windows elsewhere), so "never on reader windows" is structural, not a condition (DR-332 item 5). The call is fire-and-forget: nothing awaits it, so no window activation waits on the network (AC-153).
- **Menu item** (`components/SettingsMenu.svelte`): *Check for updates* sits between *Settings…* and *About…*, reusing the released `rescan` glyph (circular arrows — the platform's check-for-updates mark, DR-332 item 3); the shared component means the item exists in the library window and in every reader window alike (UI-50 as revised).
- **Feedback store** (`state/feedback.svelte.ts`): `notifyWithAction(key, params, action)` returns the toast id; the auto-dismiss rule changed per DR-332 item 1 — an info toast auto-dismisses only when it carries no action, so the availability toast (with its *Install* action) persists until acted on. No shipped toast carried an action before; `notify()` is unchanged.
- **i18n** (`i18n/en.ts`): `updates.available`, `updates.availableNotes` (used only when the manifest carries `body` text), `updates.install`, `updates.uptodate`, `updates.checkFailed`, `updates.installFailed`, `job.update` — all through the coverage test.

## Invariants

- The app never compares versions, parses manifests, verifies signatures or launches installers itself; `updates.ts` contains no decision logic beyond which released affordance a plugin outcome maps to.
- The startup path is silent by construction: startup failures and a current app produce no toast, no bar, no state; only a found update arms the affordance (AC-153 / UI-52).
- No window activation depends on the update check; nothing in the mount sequence awaits it.
- The availability affordance is a toast with an action — never a modal (UI-52); at most one availability toast per version is open at a time.
- An install always ends in the app exiting through the platform installer; there is no in-place swap of running code.

## Test mapping

| Layer | Coverage |
|---|---|
| Rust `cargo test` | none — the feature adds no app-side Rust logic (no custom commands; the plugin's engine is third-party, tested upstream). The manifest-entry change (DR-330) is covered by the existing build + `command_router_matches_the_ui_command_client` |
| Frontend units | none specific — `updates.ts` holds no testable pure logic; the feedback-store rule change is asserted through the flow |
| `scripts/ui-smoke.mjs` · `flowAppUpdate` (10 checks + 1 conditional skip) | **AC-151/AC-152/AC-153, UI-52:** newer manifest → the toast names the version and its notes with an Install action; current manifest → the up-to-date report; stopped server → the typed-error toast; the startup scenarios run once each (reachable current manifest, stopped server): activation measured on the page's clock within the released 3 s startup budget with the check in flight, the check-completion barrier (the harness invoking `plugin:updater\|check` through the page) observed between window creation and activation, nothing shown; then the newer-manifest startup: the armed toast, Install clicked, progress observed through the job-progress affordance to `Finished`, the app exits for the installer. The skip row fires when the binary was not built with the fixture config. The flow ends by relaunching a fresh session after the install exit (D14) |
| Fixture harness (`ui-smoke.mjs` + `ui-verify.mjs`) | `buildUpdateFixtures()`: the artifact is `System32\where.exe`'s bytes overlaid to 768 KiB (a real minimal PE — the plugin's magic-byte detection classifies it as an NSIS `.exe`; the overlay makes the download observable), served by a local endpoint at `127.0.0.1:14299` in 32 KiB writes 150 ms apart with `Content-Length`; the manifest is the dynamic form, versions from `tauri.conf.json` (`999.0.0` for "newer", the app's own version for "current"), signed once over the artifact bytes with the **product private key** (`tauri signer sign`). The endpoint override is a build-time `TAURI_CONFIG` merge (the plugin's `check` takes no endpoint argument); it is applied only when the fixture build is active — `PDFKEEPER_UPDATE_FIXTURE=1`, set by `ui-verify.mjs` for every lane, decided by a standalone run's own resolved flow selection; the build stamp records the config so the D15 staleness check rebuilds when a run wants the other config. `flowAppUpdate` sits in ui-verify's measure group and in `AREAS["keeping-up-to-date"]` |

Verified evidence (2026-11-17): activation 261 ms (reachable) / 243 ms (unreachable) against the 3 000 ms claim with the check in flight; the barrier observed in both scenarios; nothing shown in either.

## What this feature does not have (stated so nobody builds it by accident)

Automatic download or automatic install — installing is always the user's click. Release-notes browsing beyond the manifest's `notes` text. Update channels, beta tracks, or a configurable source. A background re-check while the app runs (the check runs at startup and when asked). Any update UI of its own in a reader window beyond the shared Settings menu (the menu is chrome, UI-50; the update flow surfaces through that window's own toasts). Delta/differential updates (the full artifact downloads).

## Generation (`src-tauri/src/covers/`)

- `pdfium-render` renders the cover page — **page 1, unless the document carries a manual cover choice (FR-31, §Manual cover selection below)** — at target width `RENDER_TARGET_WIDTH = 640` px — raised from 220 in v0.0.4 (D7) so the largest display size (320 px card at 2× device-pixel ratio) is a downscale, never an upscale. PNG output into `<app_data>/covers/`.
- **The render stage dispatches by document type (v0.0.9, FR-22/AC-127):** `.pdf` → pdfium page 1 as above; `.epub` → `epubmeta::cover_image` reads the cover image the package declares (the OPF `<meta name="cover">` reference resolving to its manifest item, spec §3.2/§3.3) and `compose_epub_cover` places it on the 640-wide cover canvas **contain-fit — whole, never cropped — with a transparent letterbox** (DR-299: a book cover is printed artwork; cropping it is losing content). A non-raster declaration (SVG in this release) or no declaration yields nothing — the row shows the glyph placeholder, exactly the unrenderable-document path. No pdfium call on this path — the decode is pure Rust (`image`), so the single-render-worker rule (one thread touches pdfium) is untouched and EPUB covers flow through the identical queue, encode pool, cache key and progress machinery.
- Cache key: `cache_key(path, size, mtime, width, choice_tag: Option<&str>)` — content-addressed by source file identity **plus the renderer's current target width** (FR-16 as modified by DR-113); since v0.0.12 the optional fifth part is the manual-choice tag (§Manual cover selection) — with no choice nothing is hashed and the key is byte-identical to the released function. A changed file or a changed render target produces a new key and the old PNG is swept by `sweep_orphans` (startup maintenance) — raising the render width re-keys every entry, so existing libraries re-render in the background with no explicit cache wipe.
- `pdfium_binary_present()` gates rendering: without the bundled pdfium binary the app runs fully, simply without covers (graceful degradation, no errors).
- Packaging (DR-59): `bundle.resources: ["binaries/*pdfium*"]` ships the platform library `fetch-pdfium.mjs` downloaded (`pdfium.dll` / `libpdfium.so` / `libpdfium.dylib`) into `binaries/` beside the installed exe. `bind_candidates()` binds in order: exe directory → `binaries/` beside the exe (packaged) → `cwd/binaries` (dev). Windows layout verified from an administrative MSI extraction; the installed exe runs against it.

## Queue model (D17 as shipped, DR-134)

- `CoverQueue` (`mpsc` handle, `Clone`): `import_paths` / `import_folder` enqueue a `CoverJob` after each row commit and return immediately — cover work never blocks import (DR-17).
- `start_pool(dir, sink)` starts the pipeline (D17): **one render worker** binds pdfium and produces decoded images, feeding **N PNG-encode workers** that encode and write. The split is the measured one (DR-134): pdfium load+render is 4 % of a cover's time and the bundled pdfium binary is not safe for concurrent calls (pdfium-render #262), so pdfium is touched by exactly one thread — as released in v0.0.1–v0.0.4; the PNG encode is 96 % and is pure Rust and thread-safe. Encode-pool size: default `min(4, max(1, ⌊cores/2⌋))`; the `PDFKEEPER_COVER_WORKERS` override is clamped to 1..8 (`pool_size` takes the override as an argument so the clamp is testable without process env). A bounded handoff (capacity 2 per encoder) keeps a stalled encoder from letting the renderer run ahead unbounded. `PDFKEEPER_COVER_WORKERS=1` collapses the pipeline to the released serial behavior.
- `ProgressTracker` keeps the released event contract across workers (R5.1): the queue counters and the throttle (every 25 completions + final drain, AC-33 unchanged) live in the shared tracker; a gate makes the event stream monotonic — every published count is read and stamped under one lock — and the final drain event is guaranteed. Progress goes through `EventSink::progress` → `library_job_progress` events as before. The v0.0.1–v0.0.4 single `start_worker` is gone.
- A missing pdfium binary leaves drain-only behavior: rows are counted, no images are produced, nothing errors (graceful degradation, `pdfium_binary_present()` gate unchanged).
- Startup backfill: `enqueue_missing_covers(conn, queue)` queues every document without a cache hit (e.g. after a cache directory wipe). `rescan` enqueues jobs for files whose size/mtime changed. A failed render skips that document (row shows the placeholder); it never fails the import or the batch.

## Manual cover selection (v0.0.12, FR-31 / UI-55, spec §3.8)

**Storage (`src-tauri/src/db/mod.rs`).** Migration 3 (`user_version` 2 → 3): `ALTER TABLE documents ADD COLUMN cover_choice TEXT NULL`; the baseline carries the same column. NULL means *automatic* — the released behavior; no default, no CHECK constraint: the value grammar is validated in the service boundary, not in SQL (`db::tests::v3_migration_adds_cover_choice_to_an_existing_database` — the column exists with no default, existing rows read NULL). The choice belongs to the row: rename and relink carry it (the rename SELECT list and the queue's backfill both read the column).

**Value grammar (`src-tauri/src/covers/mod.rs`).** `CoverChoice` — `Page(u32)` (a 0-based PDF page index) or `EpubImage { entry, media }` (an EPUB manifest entry plus its declared media type). Stored as JSON, exactly two shapes: `{"kind":"page","page":<0-based u32>}` or `{"kind":"epub-image","entry":"<manifest entry>","media":"<media type>"}`. `validate_choice(value, path)` is the strict command-boundary check: malformed JSON, bad grammar, or a kind that does not match the row's file type is the typed `AppError::Validation` and never reaches storage. The read sides (enqueue, sweep, the library query) parse leniently (`parse_choice`): a value that cannot be parsed behaves like no choice at all — the same designed fallback as any cover failure (R5.3). An out-of-range page or an entry the book no longer carries is *grammatical*: the render produces the **automatic** cover but writes it under the **requested choice-tagged key**, the choice stands (it never silently reverts), and the fallback is logged (FR-26, DR-404).

**Cache key.** `choice_tag(choice)`: `p<page>` for a page choice, `e<16-hex>` (the entry path hashed with the key's own deterministic hasher) for an EPUB entry. The tag joins `cache_key` only when a choice exists — with `None` the function is byte-identical to the released one, so the migration re-keys nothing and no existing library re-renders (AC-180, `covers::tests::no_choice_keys_are_byte_identical_to_the_released_function`). `CoverJob` carries `cover_choice`; `enqueue_missing_covers` and the rescan read the column and check the tagged key (`enqueue_missing_covers_reads_the_choice_column_and_checks_the_tagged_key`). A superseded automatic or old-choice key stops being referenced by any row and is swept by `sweep_orphans` as an ordinary orphan — no new staleness rule (`sweep_keeps_the_chosen_cover_and_sweeps_the_superseded_automatic_one`).

**Render dispatch.** The queue model is unchanged (one render worker, encode pool, progress contract). The worker's cover branch dispatches on the choice: `Page(n)` → `pdf::render_cover_image(..., page = n)` — pdfium already renders arbitrary pages for the reader, the canvas rules (width, max height, password gating) unchanged; `EpubImage { entry, .. }` → `epubmeta::cover_image_at(path, entry)` — the released `cover_image` generalized to an explicit entry, composition unchanged (contain-fit, DR-299); no choice → the released path (page 0 / the declared cover). The output is written under the requested key — the out-of-range fallback included, so a choice never re-queues itself in a loop (`a_chosen_page_renders_under_the_tagged_key_and_completes_without_loops`, `an_out_of_range_page_choice_renders_the_automatic_cover_under_its_tagged_key`).

**Service + commands.** `library::service::set_cover_choice(conn, queue, id, value)` — validate against the row's file type, store verbatim, enqueue the render with the new choice, return the updated DTO (its `cover_path` is the tagged key the moment the render lands; the command returns while rendering is background work — AC-180); `clear_cover_choice(conn, queue, id)` — NULL plus re-enqueue of the automatic cover under the untagged key (AC-177); `cover_candidates(conn, id)` — the EPUB manifest images the pipeline can decode as `CoverCandidateDto { entry, media_type }`, ordered by the book's **display order** per DR-411 (`epubmeta::cover_candidates`: spine-item order — the spine is reading order — with each spine document's image references in document order, first mention wins; unreferenced declared raster images follow in manifest order); a PDF is refused with a typed validation — its picker is the page-thumbnail strip (`app_pdf_thumbs`). Thin commands `app_cover_choice(id, choice)`, `app_cover_clear(id)`, `app_cover_candidates(id)` (background execution, R1.2); typed client `appCoverChoice` / `appCoverClear` / `appCoverCandidates` (`ui/src/api.ts`); `DocumentDto.cover_choice` carries the stored value so every surface knows the current choice without a second query (R1.6).

**UI (UI-55; the shape is the user's OQ-73 answer, DR-403).** Reader **cover menu** `components/CoverMenu.svelte`: a control in the reader chrome strip's right-end control cluster (left of the settings control; on macOS the whole cluster moves with it per UI-07 MODIFIED, §3.7), present only in the reader's ready state. PDF items: *Set this page as cover* (the page currently shown — valid by construction) and *Automatic cover*; EPUB items: *Choose cover…* (opens the picker) and *Automatic cover* (`reader.cover.*`). Library **cover picker** `components/CoverPickerDialog.svelte`: opened by the document context menu's *Update cover…* (`row.updateCover`, list and grid alike). PDF: a lazily filled page-thumbnail strip — `app_pdf_thumbs` windows requested through an IntersectionObserver sentinel, window 12 (≤ the backend's 32-page cap), extent from `app_pdf_document`; no strip is fetched beyond what scrolls into view. EPUB: an image grid from `app_cover_candidates`, tiles delivered through the released `bookkeeper-epub:` asset protocol (the same path the reader uses for book images — no client-side platform branch), ordered as the backend orders them; a book with no decodable image says so plainly (`coverPicker.noImages`). Tiles carry the theme's hover language (accent tint, the user's DR-408). Choosing calls `appCoverChoice` / *Automatic cover* calls `appCoverClear`; the finished cover reaches the library through the released DR-231 appearance path (`cover_path` only when the file exists + the store's cover-completion re-query) — no new refresh mechanism.

**The toolbar-dialog variant (`Modal.svelte`, DR-408 → DR-410 → DR-411 → DR-412 → DR-415).** A dialog that passes the `actions` snippet renders the toolbar shape; dialogs without actions are unchanged. The bar — the app's own toolbar language, carrying the title, every action as a button, and the close control at its right end — is **pinned**: the dialog box itself is `overflow: hidden`, the children render in a `.modal-scroll` area that owns all scrolling, so the scrollbar never runs over the bar (DR-410). The area bleeds to the dialog's side edges (negative side margins cancel the dialog's 24 px side padding) while its own padding keeps the content inset — the scrollbar sits at the dialog's edges, the released modal position (DR-411). Its vertical run stops at the dialog's content box, clear of the 14 px rounded bottom corners (`--radius-modal`) (DR-412). `scrollbar-gutter: stable` keeps rows stable whether or not the scrollbar shows. The area's top carries a 4 px `padding-top`/`scroll-padding-top` (the bar gap split 8 + 4) so the first content row is never flush on the area's overflow-clip edge (DR-415 — the user's report, measured in the running app at 175 % scaling: `input.top ≥ area.top + 4 px` after the fix). Consumers: `CoverPickerDialog.svelte` and — same day, same variant — `TagsDialog.svelte` (UI-10 MODIFIED, [tags.md](tags.md)).

## UI (`ui/src/`)

- `DocumentRow` / grid card render the cached path returned in `DocumentDto.cover_path` (mapped to a file URL in `query.rs::map_row`); placeholder tile when absent.
- **Display sizes (current):** the list cover is the v0.0.8 reversed chain, second enlarged in **v0.0.10 (UI-51, DR-320)**: `ROW_COVER_WIDTH = 100` (the user's number) → `ROW_COVER_HEIGHT = round(100 × 297/210) = 141` (the same A4 ratio) → `ROW_HEIGHT = 141 + 2 × ROW_COVER_GAP = 157` — **100×141 centered in the 157 px row with the 8 px gap**, `--row-height: 157px` mirroring the constant in lockstep (all derived from shared constants/tokens in `lib/virtual.ts` + `--row-height`/`--row-cover-gap`, so they cannot disagree; the history: 34×48 at 48 px rows in v0.0.1–v0.0.2, 45×64 at the 64 px row from v0.0.3, 51×72 at the 88 px row in v0.0.7 §3.12 DR-188/DR-189, 75×106 at the 122 px row in v0.0.8 §3.13 DR-278; see sorting-and-views.md for the row geometry); a card's cover is `coverWidth(cardWidth) = cardWidth − 2 − 2 × CARD_CONTENT_PAD` at the shipped 218:309 inner ratio — the 5 px content inset of v0.0.7 (DR-245; see sorting-and-views.md). **Changed in v0.0.4 (D6):** `.cover-wrap` no longer carries 10 px of padding — the cover fills the inner box, so the image can no longer cross the card border at wide card widths, and `cardHeight(cardWidth) = coverHeight(cardWidth) + CARD_TEXT_BLOCK` (the padding term left the formula; `virtual.test.ts`'s card-height and row-block cases were re-derived). **Changed in v0.0.4 (D7):** the rendered asset is 640 px wide (was 220), so the upscale above 220 px — the recorded limitation of v0.0.3 — is gone: every display size up to a 320 px card at 2× device-pixel ratio downscales from a render larger than it needs. `DocumentDto` still carries no size; the layout derives everything from the constants.
- Cover progress merges into the import progress UI (`library_job_progress`).
- **Cover appearance on generation completion (v0.0.7, §3.19, DR-231/DR-237).** Two halves: (1) the backend stops promising a cover file that isn't there — `query.rs::map_row` delivers `cover_path` only when the cache file exists (the released `enqueue_missing_covers` rule moved into the read path: an unprepared row carries no path, renders the glyph, and issues no asset request); (2) the store re-queries when cover work completes — `#coverRefresh` (`state/library.svelte.ts`): a trailing `debounce` (250 ms) collapses the burst of cover progress events (the queue emits every 25 + the final drain) into ONE `#refreshCoverRows()` — a re-run of the current search over the current view — so finished covers appear in the open list or grid without a reload or view switch (AC-100). The re-query is the store's own search path — no second data source, no polling.
